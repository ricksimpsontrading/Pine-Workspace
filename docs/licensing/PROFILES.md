# Licence profiles — FREE / PRIVATE / COMMERCIAL

*Français d'abord, English below. Les modèles de textes (anglais) sont dans `templates/` ; leur permission de réutilisation dans `TEMPLATE_PERMISSION.md`.*

## Français

### Principe

Un profil est une **configuration de départ**, jamais une règle de qualité ni un mode de publication imposé : gratuit ou payant, la conception, la documentation, le tutoriel et les critères de validation sont les mêmes (standard maître §5). Il ne force jamais la licence existante d'un script importé (voir « Licence existante d'un script importé »). Les axes restent séparés dans le manifeste `SCRIPT.json` (schéma 3) et s'ajustent individuellement :

| Axe | Valeurs | Rôle |
|---|---|---|
| `profile` | FREE, PRIVATE, COMMERCIAL | profil d'usage (défauts) |
| `license.id` / `license.grant` | CC-BY-NC-SA-4.0 / cc ; PROPRIETARY / none, free-use, eula ; licence existante d'un script importé / license | licence et autorisations |
| `license.origin` / `license.status` | absent ou `profile` (licence d'un profil) ; `imported` avec `confirmed` ou `to-analyse` | licence existante d'un script importé, conservée (voir plus bas) |
| `license.source_visibility` | public, closed | le code est-il publié ou livré ? |
| `license.access` | free, paid, restricted | conditions d'accès |
| `license.terms_ref` / `license.terms_url` | chemin relatif dans le produit / URL https | référence légale déclarée du produit (conditions rendues ; URL hébergée, par exemple sur le dépôt GitHub de l'auteur) |
| `publication.state` | unpublished, published, null (inconnu) | le script est-il publié sur TradingView ? |
| `publication.privacy` | public, private, null | confidentialité de la publication TradingView (fil communautaire ou non) |
| `publication.mode` | open, protected, invite-only, null | mode du script TradingView (source visible ; source masqué ; accès par invitation) |

Les trois dimensions de publication sont indépendantes : une publication privée peut être ouverte, protégée ou sur invitation. Une valeur inconnue reste `null` et est signalée (`PUBLICATION_STATE_UNKNOWN`, `PUBLICATION_INCOMPLETE`), jamais déduite. Rien n'est dérivé automatiquement ; les cohérences sont contrôlées entre axes : `mode = open` exige un source `public` ; une library est toujours `public` en mode `open` ; un accès `paid` attend une publication `public` en mode `invite-only` (règle TradingView consultée le 2026-11-06 : seul un script public invite-only peut être payant ; la vente d'un script privé est interdite) — sinon avertissement avant publication. Seule valeur dérivée pour l'affichage : la variante « FREE à source fermé » (profil FREE sous licence propriétaire `free-use`).

**Les documents suivent les axes de licence, pas le nom du profil.** La licence et l'autorisation (`license.id`, `license.grant`) déterminent les documents servis, générables et vérifiés : CC BY-NC-SA 4.0 → en-tête CC ; `free-use` → en-tête propriétaire et autorisation gratuite ; `none` → en-tête propriétaire et notice (autorisation particulière facultative) ; `eula` → en-tête propriétaire et EULA. Quand le profil décrit un autre régime que ses axes (par exemple un profil FREE sous EULA ou sans autorisation, un profil PRIVATE ou FREE à accès payant, un profil COMMERCIAL sans EULA), le scanner le signale (`PROFILE_AXES_DIVERGENCE`, avertissement) : au titulaire de confirmer lequel est juste.

Défauts de départ :

| Profil | Licence | Source | Accès | Publication (état / confidentialité / mode) | Texte de référence |
|---|---|---|---|---|---|
| **FREE** | CC BY-NC-SA 4.0 (attribution, non commercial, partage à l'identique) | public | free | unpublished / public / open | `templates/HEADER_FREE_CC_BY_NC_SA.txt` |
| **FREE à source fermé** (profil FREE, axes ajustés) | propriétaire + autorisation gratuite d'utilisation (`free-use`) | closed | free | unpublished / public / protected | `templates/FREE_USE_GRANT_CLOSED_SOURCE.md` |
| **PRIVATE** | propriétaire, tous droits réservés, aucune autorisation générale | closed | restricted | unpublished / null / null | `templates/NOTICE_PROPRIETARY_SHORT.md` |
| **COMMERCIAL** | propriétaire + EULA configurable | closed | paid | unpublished / public / invite-only | `templates/EULA_COMMERCIAL_TEMPLATE.md` |

Points d'attention :

- **CC BY-NC-SA 4.0** : Creative Commons ne recommande pas ses licences pour les logiciels ; le choix est assumé pour un script publié dont l'auteur fixe les termes, et il ne remplace pas les règles propres à TradingView (règles de publication, modération), qui s'appliquent en plus.
- **PRIVATE** dans PWS est un profil d'usage (personnel, interne, partage limité, autorisations particulières possibles). Ce n'est ni une publication privée TradingView (`publication.privacy`) ni un dépôt GitHub privé (destination d'export). Un produit PRIVATE peut rester non publié, ou être publié en privé avec un mode défini.
- **COMMERCIAL** : les droits d'utilisation et d'accès sont distincts de la propriété intellectuelle ; l'achat ne cède aucune propriété. L'EULA reste un **brouillon** tant que les champs indispensables (`release/eula-fields.json`) ne sont pas renseignés : le texte rendu porte alors un bandeau explicite « DRAFT — not for publication », il n'est jamais exporté vers GitHub, et `pine-release` le signale ; cela ne bloque pas le développement. PWS n'invente jamais d'identité légale, d'adresse, de juridiction, de politique de remboursement ni de conditions commerciales, et n'introduit ni clause universelle « aucun remboursement » ni suppression des garanties légales.
- **Référence légale déclarée** : `terms_url` est la seule URL propre au produit que le guard admet dans un source (en commentaire, correspondance exacte) — jamais un domaine entier ni « toutes les URL GitHub ». Déclarée sans conditions attachées (`terms_ref` nul), elle est signalée. Aucune URL n'est inventée pour un produit existant. Une URL de licence tierce ne se déclare jamais comme `terms_url` : elle relève de la règle des notices ci-dessous.
- **Notices et attributions tierces** : elles sont conservées mot pour mot ; une notice ne se retire jamais pour satisfaire le guard. Le guard admet, par une règle ciblée et seulement dans un commentaire, les URL de licence reconnues : textes de licence des organismes (Creative Commons, outils du domaine public dont CC0, MPL, Apache, GNU, OSI, SPDX), en `https://` comme en `http://`, et le fichier `LICENSE` / `COPYING` / `NOTICE` du dépôt d'origine sur un hébergeur de code connu quand le commentaire est une notice de licence. Aucune exemption générale d'URL : une URL promotionnelle reste bloquante, comme toute URL dans un texte affiché à l'utilisateur. Un en-tête qui porte la licence déclarée et une autre mention de licence est signalé (avertissement : notice tierce à garder ou contradiction à analyser).
- **Conditions rattachées** : `license confirm --terms-ref` ne rattache que le rendu actuel et complet du document de conditions des axes du produit (EULA, autorisation gratuite ou notice), écrit par `license write` ; un brouillon, une copie devenue non actuelle ou tout autre fichier (manifeste, décisions…) est refusé. Le statut des conditions se lit sur le document rattaché lui-même : il redevient brouillon si ce document n'est plus le rendu actuel des informations enregistrées (champ modifié, année ou identité changées), jusqu'à une nouvelle génération.
- **Écritures bornées** : `license write` n'écrit qu'un document des axes du produit, directement sous `release/` (nom par défaut ou nouveau nom ; `.md` pour les documents, `.txt` pour les en-têtes), jamais à travers un lien symbolique, et ne remplace un fichier existant qu'à la destination par défaut de ce document ou à sa copie rattachée. `license confirm` refuse une valeur qui rendrait le manifeste invalide (par exemple un mode `open` pour un source fermé) et n'écrit jamais dans un manifeste déjà cassé ; `confirm` et `set-fields` s'exécutent sous un verrou du produit, sans perte entre deux commandes rapprochées. Seuls les champs du titulaire de `release/eula-fields.json` alimentent le rendu : identité, années et URL viennent toujours du manifeste et de la configuration (une autre clé reste dans le fichier, ignorée et signalée).
- **Licence existante d'un script importé** (décision du titulaire du 2026-11-13, constat C-19 ; extension compatible du schéma 3, `schema_version` inchangé, aucun manifeste existant modifié ni migré). Les profils restent les configurations proposées aux nouveaux projets ; ils ne forcent jamais la licence d'un script importé, qui conserve son texte, ses notices, ses attributions et sa licence. Quatre notions restent distinctes : profil d'usage, licence (`license.id` exact), visibilité du source, publication (état, confidentialité, mode).
  - **Enregistrement** : `license.origin` = `imported`, `license.status` = `confirmed`, `license.id` = identifiant SPDX **exact** confirmé par le titulaire, `license.grant` = `license` (droits définis par la licence elle-même ; `cc` pour CC-BY-NC-SA-4.0). Liste fermée : MPL-2.0 (en-tête par défaut de l'éditeur Pine), MIT, Apache-2.0, BSD-2-Clause, BSD-3-Clause, GPL-2.0-only, GPL-2.0-or-later, GPL-3.0-only, GPL-3.0-or-later, LGPL-2.1-only, LGPL-2.1-or-later, LGPL-3.0-only, LGPL-3.0-or-later, AGPL-3.0-only, AGPL-3.0-or-later, et CC-BY-NC-SA-4.0 (par exemple un script d'un auteur tiers sous cette licence).
  - **Exactitude** : « only » et « or later » ne sont jamais assimilés — une notice « either version 3 of the License, or (at your option) any later version » donne `-or-later`, une notice « version 3 » seule `-only`, toute autre formulation est à analyser : plusieurs versions ou un choix entre versions (« version 2 or 3 », « v2 or v3 », « either version 2 of the License, or (at your option) version 3 », expression SPDX `GPL-2.0-only OR GPL-3.0-only`) ne donnent jamais un identifiant `-only` ou `-or-later` unique, pas plus qu'une mention « later » sans cette clause. Les identifiants SPDX dépréciés et ambigus (`GPL-2.0`, `GPL-3.0`, `LGPL-2.1`, `LGPL-3.0`, `AGPL-3.0`, et leurs formes « + » `GPL-2.0+`, `GPL-3.0+`, `LGPL-2.1+`, `LGPL-3.0+`, `AGPL-3.0+`) ne sont jamais enregistrés et restent à analyser, sur une ligne `SPDX-License-Identifier` comme dans le texte de la notice (« Licensed under GPL-3.0 »). `MIT` désigne le texte Expat : une notice X11, ou la seule mention « MIT License » (terme ambigu selon la FSF), est à analyser.
  - **« À analyser »** : licence personnalisée, ambiguë, non reconnue, variante Creative Commons autre que BY-NC-SA 4.0, plusieurs licences ou mentions contradictoires → `license.status` = `to-analyse`, `license.id` = null. L'état est explicite (avertissement `LICENSE_TO_ANALYSE`, jamais un manifeste cassé muet) : il n'empêche pas le travail courant, mais la préparation de publication et l'export attendent que le titulaire enregistre la licence exacte (`license confirm --license-id`).
  - **Proposition, jamais preuve** : la lecture de l'en-tête (`license detect`, `license overview`) propose un identifiant ; ce n'est jamais une preuve juridique et rien n'est enregistré sans la confirmation du titulaire.
  - **Conflits possibles** (licence copyleft — MPL, GPL, LGPL, AGPL — avec un source fermé ; licence copyleft, CC BY-NC-SA comprise, avec un mode `protected` ou `invite-only` ou un accès payant — pour CC BY-NC-SA, sa clause NonCommercial ; licence permissive dont la notice doit accompagner l'œuvre) : avertissements à analyser (`IMPORTED_LICENSE_CONFLICT`), jamais un blocage automatique présenté comme une conclusion juridique. Seule la règle mécanique de CC BY-NC-SA 4.0 passe avant : un source fermé sous cette licence, importée ou non, rend le manifeste cassé (`LICENSE_VISIBILITY_MISMATCH` : source `public` exigé, comme pour le profil FREE) et n'est jamais présenté en plus comme un point à analyser.
  - **Guard** : il vérifie que la notice existante est toujours présente et cohérente avec `license.id` (une notice absente, ou qui établit une autre licence de la même famille, bloque — l'enregistrement se corrige avec le titulaire, jamais la notice ; une notice qui n'établit pas exactement l'identifiant enregistré — plusieurs versions, identifiant déprécié, formulation ambiguë — donne un avertissement, jamais un blocage ni une acceptation silencieuse). La notice est lue dans l'en-tête et dans le bloc de commentaires initial qui suit la directive `//@version`, jusqu'à la première ligne de code, où ses auteurs ont pu la placer : elle n'est jamais déplacée. Il n'exige ni l'en-tête CC, ni « All Rights Reserved », ni une ligne © du titulaire configuré (les auteurs d'origine restent cités) ; la règle ciblée des URL de licence dans les notices reste celle décrite plus haut. Une licence à analyser laisse le modèle d'en-tête non vérifiable.
  - **Parcours licences** : aucun document de conditions PWS n'est imposé (ni en-tête de modèle, ni EULA, notice ou autorisation) ; `overview` et `status` affichent « licence existante conservée » (ou « à analyser »).
  - **Documents juridiques d'origine** (demande du titulaire du 2026-11-14 ; même extension compatible du schéma 3, manifestes existants inchangés) : les fichiers qui accompagnent la licence dans la distribution d'origine du script — texte de licence, `NOTICE`, attributions — restent tels quels dans le produit, à la racine ou directement sous `release/` (noms `LICENSE`, `LICENCE`, `COPYING`, `COPYRIGHT`, `NOTICE`, `PATENTS`, `AUTHORS`, `CREDITS`, `ATTRIBUTION`, `CONTRIBUTORS`, `THIRD_PARTY_NOTICES` et leurs variantes : `LICENSE.md`, `LICENSE-MIT`, `COPYING.LESSER`, `NOTICE.txt`…), ou sous `LICENSES/` (disposition REUSE : `LICENSES/MIT.txt`). Le titulaire les déclare (`license.documents`, par `license confirm --license-document <chemin>` répété ; `--no-license-documents` quand aucun document séparé n'accompagne le script ; `--clear license_documents` pour revenir à « non déclaré ») ; l'export GitHub les envoie alors **à l'identique** (même nom — `LICENSES/<nom>` conservé —, mêmes octets, même encodage, même langue ; Git ne doit pas les modifier au commit), jamais remplacés par un modèle PWS ni comparés à un modèle. Un nom juridique ne suffit jamais à inclure un fichier ; aucun n'est écarté en silence non plus, où qu'il soit dans le produit (sauf `research/`, `validation/`, `tests/`) : tant que les documents ne sont pas déclarés, qu'un fichier de nom juridique trouvé n'est pas déclaré ou ne peut pas l'être là où il est (mal placé, dossier, lien — le titulaire le déplace), ou qu'un document déclaré est absent, modifié depuis le plan, lien symbolique ou physique, fichier spécial, vide, binaire, en UTF-16/32 ou dans un encodage non compatible ASCII, porte un bandeau ou une syntaxe de modèle PWS, ou porte vers une destination publique du code Pine d'un source fermé, l'export entier attend, avec la résolution (jamais un ensemble incomplet). Un document déclaré devenu indisponible donne un avertissement (`LICENSE_DOCUMENT_UNAVAILABLE`), jamais un blocage du travail courant. L'identifiant SPDX enregistré nomme la licence ; il ne dit pas à lui seul quels documents et notices une redistribution exige.
  - Un script existant que le titulaire préfère placer sous un profil (relicence, s'il détient tous les droits — preuve à consigner) suit le chemin des profils ; une licence n'est jamais changée automatiquement.
- **Identité et année** : le titulaire (`COPYRIGHT_HOLDER`) vient de la configuration (`pws.config.json`) ; l'année de création de `license.created_year` (conservée lors des mises à jour). Une année **inconnue n'est jamais remplacée par l'année courante** : l'en-tête rendu garde `{{YEAR_RANGE}}` et reste un brouillon jusqu'à `license confirm --created-year` ; à la création explicite d'un nouveau projet, `pine-new` propose l'année courante ; une migration ne renseigne jamais l'année. La distribution de PWS n'impose jamais ses auteurs comme titulaire de vos scripts.
- **Modèles** : format volontairement minimal — `{{CHAMP}}`, blocs optionnels `[[?CHAMP:…]]` (gardé si le champ a une valeur) et `[[!CHAMP:…]]` (gardé s'il est vide), ligne de provenance `pws-template` retirée au rendu. Un document rendu déclaré final ne contient aucune syntaxe de modèle résiduelle ; un modèle mal formé produit une erreur, jamais un document. Vous pouvez reprendre, modifier et distribuer les textes rendus dans vos documents sans attribution PWS (`TEMPLATE_PERMISSION.md`). Le texte commun du modèle reste à PWS, vos ajouts et le contenu propre à votre produit sont à vous.
- **Création originale** : étudier un script accessible légalement sert à comprendre et comparer ; l'implémentation reste originale (ni copie, ni traduction ligne à ligne, ni simple renommage). Les références étudiées se tracent dans le suivi de conception, pas en crédits automatiques dans le script ; une notice légitime existante n'est jamais retirée rétroactivement.
- **Manifestes anciens** : schéma 1 (`distribution`) et schéma 2 (`license.publication` en une chaîne) sont lus et signalés ; `migrate --apply` écrit le schéma 3 en ne conservant que ce qui était **enregistré** : le mode identifiable d'une ancienne valeur (`tradingview-open|protected|invite-only`), la confidentialité privée de `tradingview-private`, l'état de `unpublished` ; tout le reste (état, confidentialité des trois modes, mode d'une valeur privée, toute la publication d'un schéma 1) reste nul et figure dans les points à confirmer. Les défauts de profil sont des **propositions** (`license status` → `publication_proposed_by_profile`), jamais des faits historiques ; les mentions observées dans l'en-tête du source (année ©, « invite-only ») sont rapportées comme références à confirmer (`header_hints`), jamais écrites. Les manifestes migrés par la version du 2026-11-06 qui avaient reçu une confidentialité déduite sont rectifiés par `m006` (traçable, idempotent) ; une valeur confirmée par `license confirm` n'est jamais remise en cause. Aucun réglage réel n'est changé sur TradingView.

### Commandes

Parcours guidé (menu `/pws → Qualité / publication → Licence et conditions d'utilisation`, skill `pine-license`) : indépendant de la préparation de publication ; il sert les quatre profils sans imposer une EULA à tous (FREE à source public : en-tête CC ; FREE à source fermé : autorisation gratuite ; PRIVATE : notice propriétaire et autorisation particulière facultative ; COMMERCIAL : EULA configurable) et conserve la licence existante d'un script importé sans lui imposer aucun document. Il consulte (`overview`), complète par groupes cohérents avec récapitulatif et confirmation groupée (`set-fields`), prévisualise (`preview`) et génère sur choix explicite (`write`, puis `confirm --terms-ref` pour rattacher le document). Le titulaire des droits (configuration) reste distinct de l'identité juridique du fournisseur (`PROVIDER_LEGAL_NAME`). Un document complet est techniquement complet ; ce n'est pas un contrat juridiquement validé.

```bash
python3 -m tools.pws_workspace license overview --slug <slug>            # état consolidé (lecture seule)
python3 -m tools.pws_workspace license status --slug <slug>
python3 -m tools.pws_workspace license preview --slug <slug> --kind header-free|header-proprietary|notice|grant|eula   # aperçu, rien d'écrit
python3 -m tools.pws_workspace license set-fields --slug <slug> --field PROVIDER_LEGAL_NAME="…" [--clear NAME] [--dry-run]
python3 -m tools.pws_workspace license write  --slug <slug> --kind eula [--dest release/<nom>.md]   # → release/EULA.md (bandeau DRAFT tant que des champs manquent)
python3 -m tools.pws_workspace license confirm --slug <slug> --terms-ref release/EULA.md [--created-year …] [--state …] [--privacy …] [--mode …] [--terms-url https://…]   # --terms-ref : rendu actuel et complet seulement
python3 -m tools.pws_workspace license confirm --slug <slug> --clear created_year|state|privacy|mode|terms_ref|terms_url|license_id|license_documents   # remet une valeur confirmée à « inconnu » (répétable)
python3 -m tools.pws_workspace license fields-skeleton > scripts/<slug>/release/eula-fields.json
python3 -m tools.pws_workspace license detect --source "scripts/<slug>/<fichier>.pine"   # proposition de licence lue dans l'en-tête (onboarding, lecture seule)
python3 -m tools.pws_workspace license confirm --slug <slug> --license-id MPL-2.0      # licence importée : identifiant exact confirmé par le titulaire (liste fermée)
python3 -m tools.pws_workspace license confirm --slug <slug> --license-document LICENSE --license-document NOTICE   # licence importée : documents juridiques d'origine déclarés (ou --no-license-documents)
```

## English

### Principle

A profile is a **starting configuration**, never a quality rule nor an imposed publication mode: free or paid, design, documentation, tutorial and validation criteria are the same (master standard §5); it never forces the existing licence of an imported script. The axes stay separate in the `SCRIPT.json` manifest (schema 3) and are adjusted individually: usage profile; licence and permissions; source visibility; access conditions; the product's declared legal reference (`terms_ref`, `terms_url`); and the TradingView publication described by three independent dimensions — **state** (unpublished / published / unknown), **privacy** of the publication (public / private) and **mode** of the script (open / protected / invite-only). A private publication can be open, protected or invite-only. Unknown values stay `null` and are reported, never inferred; nothing is derived automatically, coherence rules check the axes against each other (open mode requires a public source; libraries are public and open; paid access expects a public invite-only publication — TradingView rule checked on 2026-11-06: only public invite-only scripts can be paid, selling access to private scripts is prohibited).

- **FREE**: CC BY-NC-SA 4.0, public source, default publication public/open. Creative Commons does not recommend its licences for software; the choice is deliberate and TradingView's own rules apply in addition.
- **FREE with closed source**: same FREE profile with a proprietary regime and a free-use grant; default publication public/protected.
- **PRIVATE**: proprietary, all rights reserved; personal, internal or limited sharing; default unpublished, publication dimensions unknown until set. Not a TradingView private publication, not a private GitHub repository.
- **COMMERCIAL**: proprietary with a configurable EULA; default publication public/invite-only (the only mode TradingView allows for paid access). The EULA stays a **draft** — with an explicit "DRAFT — not for publication" banner, never exported — until the required fields are supplied; development is never blocked. PWS never invents legal identity, address, jurisdiction, refund policy or commercial terms.
- **Documents follow the licence axes**, not the profile name: CC BY-NC-SA 4.0 → CC header; `free-use` → proprietary header and free-use grant; `none` → proprietary header and notice; `eula` → proprietary header and EULA. A profile whose axes describe another regime is flagged by the scanner (`PROFILE_AXES_DIVERGENCE`, warning) for the holder to settle.
- **Declared legal reference**: `terms_url` is the only product-specific URL the guard admits in a source (in a comment, exact match) — never a whole domain or "any GitHub URL". Declared without attached terms, it is flagged. A third-party licence URL is never declared as `terms_url`.
- **Third-party notices and attributions** are kept verbatim; a notice is never removed to satisfy the guard. A targeted rule admits recognized licence URLs in comments only: licence texts of the licence bodies (Creative Commons, public-domain tools such as CC0, MPL, Apache, GNU, OSI, SPDX), over https or http, and the `LICENSE` / `COPYING` / `NOTICE` file of the original repository on a known code host when the comment is a licence notice. No general URL exemption: a promotional URL, and any URL in user-facing text, stays blocking. A header carrying the declared licence plus another licence mention gets a warning (third-party notice to keep, or contradiction to analyse).
- **Attached terms and bounded writers**: `license confirm --terms-ref` attaches only the current, complete rendering of the product's terms document written by `license write` (drafts, stale copies and any other file are refused); the terms status is read on the attached document and returns to draft when it is no longer the current rendering. `license write` writes only a document of the product's axes, directly under `release/`, never through a symbolic link, and replaces an existing file only at that document's default destination or attached copy. `license confirm` refuses a value that would make the manifest invalid and never writes into a broken manifest; `confirm` and `set-fields` run under a product lock. Only the holder's fields of `release/eula-fields.json` feed the rendering.
- **Existing licence of an imported script** (decision of the holder of 2026-11-13, audit C-19; compatible extension of schema 3, `schema_version` unchanged, no existing manifest changed or migrated). The profiles stay the configurations proposed for new projects and never force the licence of an imported script, which keeps its text, notices, attributions and licence. Four notions stay distinct: usage profile, licence (exact `license.id`), source visibility, publication (state, privacy, mode).
  - **Record**: `license.origin` = `imported`, `license.status` = `confirmed`, `license.id` = the EXACT SPDX identifier confirmed by the holder, `license.grant` = `license` (rights defined by the licence itself; `cc` for CC-BY-NC-SA-4.0). Closed list: MPL-2.0 (the Pine Editor's default header), MIT, Apache-2.0, BSD-2-Clause, BSD-3-Clause, GPL-2.0-only, GPL-2.0-or-later, GPL-3.0-only, GPL-3.0-or-later, LGPL-2.1-only, LGPL-2.1-or-later, LGPL-3.0-only, LGPL-3.0-or-later, AGPL-3.0-only, AGPL-3.0-or-later, and CC-BY-NC-SA-4.0.
  - **Exactness**: "only" and "or later" are never assimilated — "either version 3 of the License, or (at your option) any later version" gives `-or-later`, "version 3" alone gives `-only`, any other wording is to analyse: several versions or a choice between versions ("version 2 or 3", "v2 or v3", "either version 2 of the License, or (at your option) version 3", the SPDX expression `GPL-2.0-only OR GPL-3.0-only`) never give one `-only` or `-or-later` identifier, nor does a "later" wording without that clause. Deprecated ambiguous SPDX identifiers (`GPL-2.0`, `GPL-3.0`, `LGPL-2.1`, `LGPL-3.0`, `AGPL-3.0`, and their "+" forms `GPL-2.0+`, `GPL-3.0+`, `LGPL-2.1+`, `LGPL-3.0+`, `AGPL-3.0+`) are never recorded and stay to analyse, on a `SPDX-License-Identifier` line as in the text of the notice ("Licensed under GPL-3.0"). `MIT` designates the Expat text: an X11 notice, or the bare words "MIT License" (an ambiguous term according to the FSF), is to analyse.
  - **"To analyse"**: custom, ambiguous or unrecognized licence, Creative Commons variant other than BY-NC-SA 4.0, several or contradictory licences → `license.status` = `to-analyse`, `license.id` = null. The state is explicit (`LICENSE_TO_ANALYSE` warning, never a mute broken manifest): current work continues; release preparation and export wait for the holder to record the exact licence (`license confirm --license-id`).
  - **A proposal, never a proof**: reading the header (`license detect`, `license overview`) proposes an identifier; it is never a legal proof and nothing is recorded without the holder's confirmation.
  - **Possible conflicts** (copyleft licence — MPL, GPL, LGPL, AGPL — with a closed source; copyleft licence, CC BY-NC-SA included, with a `protected` or `invite-only` mode or paid access — for CC BY-NC-SA, its NonCommercial clause; permissive licence whose notice must travel with the work): warnings to analyse (`IMPORTED_LICENSE_CONFLICT`), never an automatic block presented as a legal conclusion. Only the mechanical rule of CC BY-NC-SA 4.0 comes first: a closed source under that licence, imported or not, makes the manifest broken (`LICENSE_VISIBILITY_MISMATCH`: source `public` required, as for the FREE profile) and is never also presented as a point to analyse.
  - **Guard**: checks that the existing notice is still present and coherent with `license.id` (a missing notice, or one that establishes another licence of the same family, blocks — the record is corrected with the holder, never the notice; a notice that does not establish the recorded identifier exactly — several versions, a deprecated identifier, an ambiguous wording — gives a warning, never a block nor a silent acceptance). The notice is read in the header and in the initial comment block that follows the `//@version` directive, up to the first line of code, where its authors may have put it: it is never moved. The guard never requires the CC header, "All Rights Reserved" nor a © line naming the configured holder (the original authors stay cited); the targeted rule for licence URLs in notices is unchanged. A licence to analyse leaves the header model unverifiable.
  - **Licence path**: no PWS terms document is imposed (no header template, EULA, notice or grant); `overview` and `status` show "existing licence kept" (or "to analyse").
  - **Original legal documents** (holder's request of 2026-11-14; same compatible extension of schema 3, existing manifests unchanged): the files that accompany the licence in the script's original distribution — licence text, `NOTICE`, attributions — stay as they are in the product, at its root or directly under `release/` (names `LICENSE`, `LICENCE`, `COPYING`, `COPYRIGHT`, `NOTICE`, `PATENTS`, `AUTHORS`, `CREDITS`, `ATTRIBUTION`, `CONTRIBUTORS`, `THIRD_PARTY_NOTICES` and their variants: `LICENSE.md`, `LICENSE-MIT`, `COPYING.LESSER`, `NOTICE.txt`…), or under `LICENSES/` (REUSE layout: `LICENSES/MIT.txt`). The holder declares them (`license.documents`, through `license confirm --license-document <path>` repeated; `--no-license-documents` when no separate document accompanies the script; `--clear license_documents` to return to "not declared"); the GitHub export then sends them **verbatim** (same name — `LICENSES/<name>` kept —, same bytes, encoding and language; git must not change them when committing), never replaced by a PWS template nor compared with one. A legal-document name never includes a file by itself; none is left out silently either, wherever it lies in the product (except `research/`, `validation/`, `tests/`): while the documents are not declared, a file with a legal-document name found in the product is not declared or cannot be declared where it is (misplaced, a folder, a link — the holder moves it), or a declared document is missing, changed since the plan, a symbolic or hard link, a special file, empty, binary, in UTF-16/32 or in an encoding that is not ASCII-compatible, carries PWS draft or template syntax, or carries towards a public destination the Pine code of a closed source, the whole export waits, with the resolution (never an incomplete set). A declared document that became unavailable gives a warning (`LICENSE_DOCUMENT_UNAVAILABLE`), never a block of current work. The recorded SPDX identifier names the licence; it does not establish by itself which documents and notices a redistribution requires.
- **Templates**: rendered documents strip the template provenance line; you may reuse, modify and distribute them in your product documents without PWS attribution (`TEMPLATE_PERMISSION.md`). The common template text stays PWS's; your additions and product-specific content are yours.
- **Guided path** (`/pws → Quality / publication → Licence and terms of use`, skill `pine-license`): independent of publication preparation; view, complete (grouped dialogue, recap, grouped confirmation), preview and generate the documents of the profile — no EULA imposed on free or private profiles; the copyright holder stays distinct from the provider's legal identity; a complete document is technically complete, not a legally validated contract.
- **Legacy manifests**: schema 1 and schema 2 are read and flagged; `migrate --apply` writes schema 3 keeping what is known and leaving unknown dimensions null, with the points to confirm. No real TradingView setting is changed.
