# WORKSPACE ARCHITECTURE — decisions and reasons

Status: derived, architectural. Construction contract: `BOOTSTRAP_SPEC.md` (same folder). This document explains WHY, not how (the procedures are in the skills, `OPERATIONS.md`, `INSTALL.md` and `MIGRATION.md`). Revision of 2026-11-06: consolidated evolution (personal configuration, licence profiles, verification levels, deterministic menu, PineTS tools, GitHub export, archives, distribution).

## Authorities

- **A single master** (`standards/PINE_SCRIPT_V6_STANDARD.md`): any copy would create a second constitution that would drift. Neutral edition: the "holder" replaces any named identity; the real identity comes from `pws.config.json`. The rules, skills and agents route to it; the guard applies only its mechanizable rules. `INDEX.md` (generated from the real headings) and `TRACEABILITY.md` (semantic analysis) are derived, hashed against the master, and declared STALE as soon as the SHA diverges.
- **No `@` import of the master in CLAUDE.md**: an import is loaded in every session — a permanent contextual cost for content consulted occasionally.
- **Project independence** (spec §2.10): no configuration, procedure or test requires the existence, the name, the path or the state of another project. The physical boundary is controlled by the tooling (enclosing parent repo → stop; outgoing symlinks → refused; symlinked `scripts/` → nothing is read; a manifest's source resolved outside the product root → never read) and tested with paths containing spaces.

## Personal configuration separate from Claude Code

`pws.config.json` (spec §19A) carries what belongs to PWS and to the person: the holder's identity (header marks), language, TradingView mode, GitHub destinations, cleanup preference, migrated workspace version. `.claude/settings*.json` now carry only the permissions and approvals of Claude Code. Reasons: a single write controller (lock, refusal in case of conflict) for a file without an external writer; a distribution that contains no personal data by construction; a migration that preserves identity, language, products and settings because they are **configured**, not assumed. Without a file, honest defaults apply (English, `manual`, unconfigured identity → UNVERIFIABLE copyright checks).

## Licence profiles: defaults, not quality levels

Three profiles (FREE, PRIVATE, COMMERCIAL) and five separate axes in `SCRIPT.json` schema 3 (spec §45.2: usage profile, licence and permission, source visibility, access, publication — the latter in three independent dimensions: state, privacy, mode). Separating the axes allows the "FREE with closed source" case without a fourth profile and prevents confusing PRIVATE (usage) with a private TradingView publication or a private GitHub repository. Mechanical consistency lives in a single module (`profiles.py`) shared by the scanner, the guard (header marks derived from the licence and from the configured identity), the menu, the text templates (`licensing.py`) and the migration (explicit v1 / v2 → v3, step m005, ambiguities reported). An incomplete EULA is a flagged draft, never a block on development nor an invention of terms. The "Licence and terms of use" guided path (`pine-license`, 2026-11-07) views, completes, previews and generates these texts independently of publication preparation, reusing the same module, the same manifest and the same fields file — neither a second logic nor a second storage.

## Conditional context and verification levels

- **Path-scoped rules**, **procedures in the skills**, **large volumes in fresh subagents**: unchanged in their principle (layered model rule = reminder, skill = procedure, guard = enforcement).
- **Three levels** (master §9.1): routine work, for any task class (structural change included), reads in a targeted way starting from the product map (`ARCHITECTURE.md`), checks the diff and chains neither a full reading, nor an agent, nor a cascade of reviews; the deep audit (`pine-audit`) is triggered only by an explicit request and announces its scope; publication preparation (`pine-release`) carries the final requirements. Reason: systematic global reading and automatic reviews imposed a cost on every small modification without any demonstrated additional guarantee; the mechanical protections (guard, Stop hook, integrity of the validations) remain unchanged.
- **Source comments** (master §24.5): the work log lives in the tracking artefacts; the guard flags it without blocking.

## Deterministic menu

The structure of the menu is computed by `menu.py` (applicable entries, four-option pagination with `Retour` (Back) on every screen below the first level, labels and short descriptions through `i18n.py`, configuration settings with current value and canonical choices, script choice screens) and rendered by the `pws` skill. Reason: a single workflow logic with translation resources, a testable action → script path, no hard-coded product, a first level that never presents a product as the only scope, and visible texts without internal names (skills, commands, hashes), which remain in the instructions and the detailed results. The banner (`banner.py`, 2026-11-07 / 08) is a purely visual improvement with two distinct uses: the **fixed** "PWS" banner of the `/pws` menu (a 23-column FIGlet Standard constant — text "PWS" since the holder's decision of 2026-11-14, formerly "Pine-WS" —, provided as `banner` data by `menu --json` and passed as is by the skill in the text of the main menu question, `banner.question`, without adaptation to the width — holder's decision of 2026-11-08, replacing the plain-text fallback for `/pws` only; free text emitted before a tool call is not used: the Claude Code presentation layer rewrites it, finding of 2026-11-08), and the adaptive PINE-WORKSPACE variants of the `banner` subcommand for a terminal (FIGlet Standard, FIGlet Small, plain text, chosen according to the width actually measured at each display on the output that receives it, with an explicit margin; captured output or tool pseudo-terminal → plain text; known width smaller than the name → nothing). It modifies neither the structure, nor the identifiers, nor the navigation, and enters a structured output only as data, never as a prefix.

## Three verification layers

- **Deterministic checks** (`tools/pws_workspace`): reliable mechanical facts; parser uncertainty produces `UNVERIFIABLE`, never a false `BLOCKING`. The diagnostic never repairs automatically.
- **Local behavioural execution** (`tools/pine_exec` + `pine-local-test`): capability-gated; ZERO GATING capability as of 2026-11-06. The identity of the executor actually installed is verified beyond the version number (lockfile, registry integrity, SHA of the installed artefact recorded in `PROVENANCE.json`, fingerprint). The lifecycle of the engine (`tooling.py`) is explicit: update search on request, installation of a chosen version after a restore point, dependent calibrations switched to STALE, byte-for-byte rollback. CURRENT never means GATING.
- **TradingView validation** (`tv-validate`): the only final empirical layer; `stale` derived, never persisted.

## Stop hook: finding-by-finding attribution

Unchanged (spec §41.2, §41.3): the Stop hook blocks only on the blocking guard findings introduced during the session. The guard now evaluates the headers according to the licence of the manifest and the configured identity; the session hashes traverse the same physical tree as the scanner (no folder symlink followed).

## Cleanup and archives

Startup cleanup is a deterministic allowlist (`__pycache__`, `.DS_Store`, stale session snapshots), locked, logged, silent when it takes no action: no analysis by an agent, no purge of archives. External archives are grouped under `docs/maintenance/archives/` by a verified procedure (inventory, references, copy, hashes, index of moves, deletion of the source only after complete verification); exact duplicates are copied only once. These local archives do not replace a backup independent of the disk.

## Git local-first and explicit GitHub export

No remote in the workspace, no remote CI. GitHub is not a dependency: it is a configured **export destination**, served by an explicit guided path (plan from a list of contents allowed per profile, included/excluded preview, local clone, diff, publication only after authorization; `git push` subject to confirmation; no token stored). A closed source never goes to a public destination. Two distinct checks precede a send: the identity of the authorized repository, for any send (the clone and the URL of the destination must designate this repository, re-read just before the push — 2026-11-14), and the privacy that closed content requires (GitHub queried, I-06); a single mechanism reads the remote. An imported script leaves with its original legal documents declared by the holder, as is: PWS never rewrites or translates the text of a third-party licence.

## Generated public distribution

The distribution (`build-distribution`) is generated from the common core by allowlist: same tooling, same skills, same neutral authorities, `install.py` installer, licences of the original components (Apache-2.0 for the core; AGPL-3.0-only for the PineTS adapter `tools/pine_exec/*.mjs`, holder's decision of 2026-11-13 — `NOTICE`, `docs/licensing/LICENSING.md`), third-party notices (PineTS engine AGPL-3.0-only: declared, never embedded; the adapter loads it in its own Node process; the core never loads PineTS: its Python tooling launches the adapter as a separate process and exchanges files and JSON, its tests contain short JavaScript programs that import modules of the adapter). Excluded by construction: products, `docs/maintenance`, runtime, personal configuration, bootstrap evidence. A post-copy check looks for personal data in three families kept distinct (revision of 2026-11-07 after an independent build from an account named `agent`): the absolute personal paths of any account; the explicit traces of the system account that builds, only in a personal context (path component, `~account`, `account@host`, environment assignment) and never as a mere word, so that a common account name does not turn an ordinary word of the code or of the documentation into a leak; the identity deliberately configured in the workspace, distinctive by choice, searched for everywhere. The account name is injectable so that the tests simulate a deterministic environment instead of depending on the real user. Reason: avoid two durably diverging implementations between the personal installation and the distribution.

## Distributed registration, on-demand folders, absent layers

Unchanged: no central registry (truth in `scripts/<slug>/SCRIPT.json`); `research/`, `docs/`, `release/`, `tests/behavioral/`, `DECISIONS.md` on demand; ratified exclusions (spec §58: GitHub as a dependency, GitHub Actions, project MCP, Agent Teams, dynamic workflows, remote CI, SQLite, local server, dashboard, custom plugin, TradingView publication automation, parallel editing agent, persistent memory of the reviewers, semantic rules engine). `pinets-cli`, Vela, edge-stats and LuxAlgo MCP: documented place only, no generic extension infrastructure.

## Guided update of the core and publication (2026-11-08)

The "Update Pine-Workspace" guided path (`update.py`, `pws-update` skill, "Tools and updates" submenu generated next to PineTS) adds no copy, backup or restoration mechanism: it orchestrates `upgrade` (code) then `migrate` (data), the two existing authorities, and stops between the two if a migration falls outside the approved plan — the whole is not atomic and is never presented as such. Reasons: a search that is always explicit and dated (never at startup, never "up to date" by default), provenance distinguished from integrity (the assets must come from the official repository and tag, the published SHA-256 hash is compared, but no signature exists and authenticity is not proven; a local package is verified only offline), an extraction inspected before any write, a plan bound by hash to the holder's agreement, and the development upstream recognized by the absence of a core manifest, never by a path. On the maintainer side, `release.py` (`build-release`) produces the artefacts of a version from the existing distribution — archive, hash, `RELEASE.json`, notes drawn from `CHANGELOG.md` — and refuses a number inconsistency; publication (tag, release, send) remains an explicit act, never executed by the tool. The version number has a single source (`version.py`); everything else derives from it.

## Guided updates of Pine Workspace and PineTS (2.2.0)

`update_guide.py` and `pinets_guide.py` chain the existing stages into one path (state, search, preparation and plan, one confirmation, application, summary) and turn their results into short summaries in the configured language (`guide_text.py`, merged into the i18n catalogue). They own no mutation: Pine Workspace still goes through `update` → `upgrade` / `migrate`, PineTS through `tooling.install` (verified rollback point) and `tooling.verify`. `recalibration.py` executes the comparisons that `pinets recalibrate-plan` listed, from the contract `tools/pine_exec/calibration/comparisons.json`, and is the only writer of CURRENT statuses after an engine change — for the capabilities actually re-exercised with success only. Reasons: one confirmation bound to a hashed plan instead of a sequence of commands to know; honest accounts once the disk changed; no second installer or restoration mechanism to keep consistent.
