# OPERATIONS — recurring procedures

Concise human document. The Pine development rules live in `standards/PINE_SCRIPT_V6_STANDARD.md`; the detailed workflows in `.claude/skills/`; the installation in `INSTALL.md`; the migrations in `MIGRATION.md`.

## Launch

Pine Workspace is autonomous: no sibling project required. Always launch from its own physical root (any path, spaces allowed):

```bash
cd "<workspace folder>"
claude                      # normal session — the PWS state is displayed at startup (configured language)
/pws                        # guided menu: action first, then script
```

A resume, a compact or a clear does not reopen the menu automatically. At launch, the deterministic cleanup (allowlist: `*.pyc` files stored directly in a `__pycache__/` under `tools/`, `.DS_Store`, session snapshots in the hook format unused for 7 days — date of last use, refreshed by the Stop hook at the end of each turn —, never that of the current session nor that of `latest.json`; any item cited by a text file tracked by Git is kept) runs and is reported only if it has acted.

## Personal configuration (`pws.config.json`)

```bash
python3 -m tools.pws_workspace init --language fr|en [--copyright-holder "…"] [--alias "…"]   # first time
python3 -m tools.pws_workspace config show
python3 -m tools.pws_workspace config set language en
python3 -m tools.pws_workspace config set identity.copyright_holder "…"
python3 -m tools.pws_workspace config set maintenance.startup_cleanup false
```

Separate from the Claude Code settings (`.claude/settings*.json`: permissions and approvals only). Not versioned, copied into the worktrees. Without the file: English, TradingView mode `manual`, identity not configured (copyright checks UNVERIFIABLE, never blocking).

## Common tasks

- **Add an existing `.pine`**: create `scripts/<slug>/`, put the file in it; it will be detected UNREGISTERED (SessionStart or doctor) and onboarded through `pine-onboard` (`/pws → Nouveau / importer → Importer`; in English: New / import → Import a script).
- **New product**: describe the goal or `/pws → Nouveau script` (in English: New script) → `pine-new` (type, then profile FREE / FREE with closed source / PRIVATE / COMMERCIAL).
- **Diagnostic**: `python3 -m tools.pws_workspace doctor` (BLOCKING = actionable; INFO = declared limitation; never repairs).
- **Compact state**: `python3 -m tools.pws_workspace session-status`; **menu**: `menu --json` (its `banner` field carries the **fixed** "PWS" banner of the menu, FIGlet Standard, 23 columns, and `banner.question`, full text of the main menu question passed on as is by `/pws`; no adaptation to the width).
- **Banner in a terminal** (use distinct from the menu banner): `python3 -m tools.pws_workspace banner` (adaptive PINE-WORKSPACE variants: wide, compact or plain text depending on the terminal width measured at each display; `--json`: structured form). Purely visual: no JSON output and no hook is prefixed with it.
- **Update Pine-Workspace**: `/pws → Maintenance / configuration → Outils et mises à jour → Mettre à jour Pine-Workspace` (in English: Maintenance / configuration → Tools and updates → Update Pine-Workspace; dedicated section below).
- **Tooling tests**: `python3 -m unittest discover -s tools/tests -t .` (from the root).
- **Licences**: guided path `/pws → Qualité / publication → Licence et conditions d'utilisation` (in English: Quality / publication → Licence and terms of use; `pine-license`, independent of publication); `license overview --slug <slug>` (consolidated state, read-only); `license status --slug <slug>`; `license preview|render --slug <slug> --kind header-free|header-proprietary|notice|grant|eula` (preview, nothing written); `license set-fields --slug <slug> --field NAME=value … [--clear NAME] [--dry-run]` (holder's fields in `release/eula-fields.json`, existing values kept); `license write --slug <slug> --kind <kind>` (→ `release/EULA.md`, `release/FREE_USE_GRANT.md`, `release/NOTICE.md`, `release/HEADER_*.txt`; draft as long as essential fields are missing); `license confirm --slug <slug> [--state …] [--privacy …] [--mode …] [--created-year …] [--terms-ref <path>] [--terms-url <https>]` (facts confirmed in the manifest).

## Reading the statuses

- `product_structure_status`: `REGISTERED` / `INCOMPLETE` / `BROKEN` / `AMBIGUOUS`. The synthetic value never overwrites the detailed list of findings. A schema 1 manifest is still read (derived profile, finding `MANIFEST_LEGACY_SCHEMA`) until `migrate --apply`.
- `profile` / `license`: FREE | PRIVATE | COMMERCIAL and the five axes; `EULA_DRAFT` and `ACCESS_PAID_WITHOUT_EULA` are warnings (never blocking for development, to be settled before a commercial publication).
- `source_registration_status`: `REGISTERED` / `UNREGISTERED` (orphan → onboarding required before substantive editing).
- TradingView validation: persisted ∈ `unverified / in-progress / passed / failed / partial`; `stale` is DERIVED; integrity `BROKEN` → never `passed`.

## TradingView mode

- Current mode: `python3 -m tools.pws_workspace tv-mode` (configuration; source `config`, `legacy` or `default`). A choice made through `tv-mode <mode>` records its provenance (`tv_validation_mode_choice`): it is this choice that resolves a legacy-value conflict flagged by `migrate --plan` (m001 blocked, never resolved automatically).
- Change (reserved for the holder): `/tv-mode manual` or `/tv-mode chrome-experimental`, or `/pws → Maintenance / configuration → Configuration → Mode TradingView` (in English: Maintenance / configuration → Configuration → TradingView mode). Same atomic controller (lock of `pws.config.json`, refusal in case of conflict). `manual` remains the default; `chrome-experimental` remains explicitly optional.
- **Manual validation**: `tv-validate` prepares the matrix suited to the change; the holder executes in TradingView and reports their actual observations; the run is tied to the SHA-256 of the source.
- **chrome-experimental validation**: requires `claude --chrome` and the connected extension. Any ambiguous case → manual fallback of the run, persistent mode unchanged. Publication always excluded.

## Verification levels

1. Routine work (`pine-develop`): targeted reading, diff, guard; PineTS only if planned.
2. Deep audit (`pine-audit`): explicit, announced scope (global reading, cartographer, reviewer, PineTS if included).
3. Publication preparation (`pine-release`): single consolidated global coverage, release review, re-checked TradingView rules, validation of the final SHA.

Guard (`python3 -m tools.pws_workspace guard "scripts/<slug>"`, same rules as the Stop hook): the manifest is read after validation (BROKEN manifest = `manifest` BLOCKING); CC mention and URL checked exactly, the © line names the copyright holder; an unrendered template field (`{{YEAR_RANGE}}`…) blocks; BOM tolerated; licence URL of a third-party notice allowed by a targeted rule (recognized licence URL — http included, CC0, SPDX, LICENSE file of a repository on a known host — in a notice comment line), never by a general exemption: a promotional URL remains blocking; a header carrying a licence other than the manifest's blocks with a holder-decision label (licence to analyse, never remove or replace an existing notice); a third-party notice next to the declared mentions, contradictory mentions (`header-consistency`) or a promotional contact (`no-promo-contacts`) give a warning.

## Integrated tools (PineTS)

- State: `tooling-status` (Node/npm, pin, lockfile, installed version, SHA of the installed artefact, provenance, calibration, restore points with their usability, last dated update search). Three distinct pieces of information: the local state (installed, integrity, calibration), the availability of an update (only according to a recorded explicit search, with its date; without a search, it is unknown — never "up to date" by default) and the usable restore points.
- Verification: `pinets verify` (`--record` records the SHA of the artefact in `PROVENANCE.json` for the first time); also checks `PROVENANCE.pinned_version` = pin and the leftovers of an interrupted rollback (WARNING); same severities as the doctor: different artefact BLOCKING, artefact missing with `node_modules` WARNING, engine missing INFO. `tooling-status` reads the integrity at each call (`artifact_check`); `provenance_verified_at` is the date recorded in `PROVENANCE.json`, never a verification made on this machine; the freshness is never CURRENT for a missing engine or a different artefact.
- Update: `pinets check-update` (explicit network access, installs nothing; dated result recorded in `.claude/runtime/tooling/last-update-check.json`) → `pinets install <version> --yes` (restore point, `npm install --save-exact --ignore-scripts`, `npm ci --ignore-scripts`, check of the resulting engine — pin, lockfile and integrity, `node_modules/pinets`, artefact — before any write of the provenance and of the STALE calibrations, otherwise failure with the state and the restore point); `check-update` compares numerically with the current pin: only a strictly newer stable version is an update, any response without a usable exact version is an error and nothing is recorded → `pinets recalibrate-plan` (read-only plan) → `pinets verify` → tests. Since 2.2.0 these commands are chained by the guided path below; they stay available for advanced use.
- Rollback: `pinets rollback <version> --yes` — two-phase restoration of a **usable** restore point from `.claude/runtime/pinets-rollback/<version>/`. Usable = `ROLLBACK_MANIFEST.json` manifest in the current format (2: SHA-256 hash of each file of the engine and of the entire `node_modules` tree, symbolic links recorded with their target), complete and verified against the backed-up content (confined paths, nothing unknown in the tree). First phase, under the lock shared with `upgrade`/`migrate`: full validation of the point, verified backup of the current engine (`before-rollback-<timestamp>`), copy prepared next to the engine and verified — a single anomaly refuses everything, the active engine is not modified (`stage: refused`). Second phase: atomic renames then final verification of the active engine (files, complete tree, artefact); success declared only once verified (`stage: verified`); an error after the first rename is flagged `incomplete` with the recovery elements kept (point, pre-rollback point, `.restore-*` and `node_modules.replaced-*` trees). A point set up by hand (for example the 0.9.33 one with its files under `tracked/`) or in format 1 (file names and artefact hash only) is listed as not usable with its reason, refused by the command, never converted by recomputing the hashes of its current content: documented manual procedure. `pinets install` refuses to start without a verified point of the current engine; an old point of the same version is kept as is and a new timestamped point is created next to it. Default rollback: the point actually backed up by the last installation (`previous_pin.rollback_point`), otherwise the most recent usable point backed up by an installation for the previous pin, never a `before-rollback-*`. Refusal if `.claude/runtime/pinets-rollback` or a parent is a symbolic link or goes outside the workspace. An interruption (Ctrl-C) before the renames yields `refused`, during them `incomplete`; the `.restore-*` and `node_modules.replaced-*` leftovers are flagged by `verify`, the doctor and `tooling-status`, never deleted automatically.
- Interpret honestly: `PINETS_EXECUTION_PASS` ≠ TradingView-validated; no modification of an indicator to satisfy a divergence of the engine.
- Guided update (2.2.0): `/pws → Maintenance / configuration → Tools and updates → PineTS`; Claude Code chains `pinets guide --stage state`, `--stage search`, `--stage prepare [<exact version>]` and, after one confirmation of the plan, `--stage apply --plan-file <plan> --yes`. The preparation installs nothing: registry metadata, npm archive downloaded outside the workspace (`npm pack`, scripts disabled) and compared with the registry integrity, archive read without extraction (package.json, LICENSE, the artifact loaded by the adapter and its hash), Node / npm prerequisites, licence compared with the recorded assessment (a different identifier, or no recorded reference, stops the plan; a different LICENSE text with the same identifier stops it too, the difference is shown, and only an explicit decision of the holder bound to that exact text — `--accept-license-text <sha256>` — lets a new plan be prepared, the decision being recorded in the plan; the recorded copy is never changed), release notes of the repository declared by the package (absent notes are said absent), recalibration cases; the plan is written with a hash and, when it includes the recalibration, bound to the comparison contract and every source, dataset and reference it names. The application re-checks the engine, the archive and that binding before the first change and again under the shared lock, saves the verified rollback point (nothing installed without it), installs through `pinets install`, checks the engine obtained against the archive of the plan (registry integrity, artifact hash, licence text) and `pinets verify`, then recalibrates. Statuses: `completed` (only when every case is concordant AND the calibrations were written and re-read as decided), `installed-verified` (recalibration not planned: calibrations STALE), `recalibrated` (recalibration alone), `refused-before-mutation` (nothing changed), `install-failed` (the engine may have changed: state on disk and rollback point given), `verification-failed`, `recalibration-divergent`, `recalibration-incomplete`. No automatic rollback: the verified point is named with its command.
- Guided recalibration: `pinets guide --stage prepare --recalibrate-only`, or included in an update plan. The cases, datasets and independent references are the existing ones, named in `tools/pine_exec/calibration/comparisons.json` and hash-checked against `case_artifacts` before any run; the comparison rules restate the existing contract (exact, or the documented tolerance of `ta-ema`) and are never relaxed; NaN, infinities, wrongly typed values and missing fields are invalid (na is allowed only on both sides). A run report is used only when it is coherent with its exit code and names the engine actually executed, the adapter's normalization schema, the executor fingerprint computed for the run, and the calibrated source and dataset; otherwise the case is not concluded. Only the capabilities actually re-exercised with success become CURRENT; the others become or stay STALE; `capability_status` and `known_divergences` are never changed and CURRENT never becomes GATING; runs, comparison and the previous `capabilities.json` are kept under `.claude/runtime/pinets-recalibration/<stamp>/`. A divergence or an unconcluded case stops that part for the holder's decision; no Pine source is modified to satisfy PineTS.
- Not installed, place documented only: `pinets-cli`, Vela, edge-stats, LuxAlgo MCP.

## Archives and cleanup

- Cleanup: `maintenance cleanup` (plan) / `--execute`; allowlist only; log `.claude/runtime/maintenance/cleanup-log.jsonl`.
- Import of external archives: `archives-plan` → `archives-import` → `archives-verify` → `archives-remove-source`. Relations refused at each step, by physical identity: source equal to the workspace, inside it or containing it, source inside another PWS installation or containing one, source given through a symbolic link, target outside `docs/maintenance/archives`. The deletion redoes the inventory of the CURRENT content of the external folder and refuses any new, modified or unverifiable file; it deletes, file by file, only what has just been verified as archived, then the emptied folders — never a recursive deletion. A stale plan (folder recreated or content changed) is refused. Cumulative index: `docs/maintenance/archives/INDEX.md`, `MANIFEST.json`. The old reports keep their original paths.
- Four notions not to be confused for `docs/maintenance/archives/`: (1) **local storage** — the files live in the workspace tree; (2) **tracking by Git** — they are not ignored (`.gitignore` must never exclude an archive or a piece of evidence, FILE_CONTRACTS) and will be tracked at the next commit decided by the holder; the weight (211 MB of binary files) is an accepted consequence of the choice to version them, any other policy (Git LFS, separate repository) is a distinct decision to be taken before commit, never a `.gitignore` added silently; (3) **backup independent of the disk** — neither the local folder nor local Git stands in for it; (4) **exclusion from the public distribution** — `docs/maintenance/` is never shipped (`build-distribution`).

## GitHub

- Connection: `github status` (gh or credential helper; no token displayed or stored; the credential helper is shown only by its name, an inline helper (`!…`) or a value carrying a password or a token is masked). Establish the connection yourself (`! gh auth login`).
- Destinations: `github destinations`, `destination-add --name … --repo owner/name --visibility public|private [--path-prefix …]`.
- Export: `github export-plan --slug <slug> --destination <name>` (included / excluded / staging) → `github fetch --destination <name>` (local clone, explicit network access) → `github export-diff` → `github publish … --yes` (only after explicit authorization; `git push` remains subject to confirmation).
- A `closed` source is never exported to a `public` destination, neither directly nor through a copy, a link or a document that reproduces its code.
- The plan (`PLAN.json`, format 2) is tied to the effective destination (name, repository, visibility, branch, prefix, URL), to the licence and to the hash of each file: `export-diff` and `publish` re-read the configuration and the manifest, recompute the plan and refuse any deviation (action: redo `export-plan`). The local clone must have the configured URL as `origin`, the right branch and no unpublished work, otherwise refusal (action: `fetch` or examination of the clone). The push explicitly targets the configured branch.
- Destination identity for **every** send (holder's request of 2026-11-14), public content included: `export-diff` (presented in `destination_check`) and `publish --yes` (redone just before any write in the clone) refuse when the clone's remote does not have a single fetch URL and a single push URL as Git uses them (`pushurl`, `insteadOf`, `pushInsteadOf` applied, global configuration included), or when these URLs and that of the destination do not designate, in the strict forms below, the configured repository. The same, single remote check as for a closed source; GitHub is not queried for public content, which may go to a public destination or to a private repository chosen explicitly. `publish` re-reads the remote just before `git push`: if it has changed after the local commit, nothing is pushed and `state_left` describes the state left on disk (clone, branch, commit, files written, unpublished work, plan kept, next steps); the holder inspects and abandons this commit themselves before a new `fetch`. Also refused: an empty URL entry; a setting that makes Git connect elsewhere than the displayed URL or without verifying it (`core.sshCommand`, `core.gitProxy`, `remote.origin.vcs`, `http.curloptResolve`, `http.sslVerify` set to false, variables `GIT_SSH`, `GIT_SSH_COMMAND`, `GIT_PROXY_COMMAND`, `GIT_SSL_NO_VERIFY`); a target that differs only by case from an entry of the repository or that requires a folder where it has a file; a file whose bytes Git would modify at commit (`.gitattributes`, `core.autocrlf`, filters). No hook runs during the commit and the push of the clone; the commit is verified before the push (a single new commit, only the paths of the plan, exact bytes). Limitations: a change made in the instant between the last read and the push itself is not detected; the offline check sees neither a repository renamed or transferred on GitHub, nor `~/.ssh/config`, nor a compromised environment.
- Closed source (I-06, holder's decision of 2026-11-13): a send that contains a closed source (source of the product whose `source_visibility` is not `public`, public source that reproduces the closed source of another product, or document carrying Pine code of a closed source; manifests re-read at the time of the send) requires that the clone's remote have a single fetch URL and a single push URL as Git uses them (`pushurl`, `insteadOf`, `pushInsteadOf` applied), both — like the URL of the destination — written exactly in one of the forms `https://github.com/<owner>/<repo>[.git][/]`, `git@github.com:<owner>/<repo>[.git]`, `ssh://git@github.com/<owner>/<repo>[.git]` (without credentials or any other user part, port, query, fragment or `%` encoding) and designating the configured repository, then that `gh repo view https://github.com/<owner>/<repo> --json nameWithOwner,visibility,isPrivate,url` (current `gh` authentication, never `gh api`) report this repository itself as `PRIVATE` (`isPrivate: true`). Otherwise refusal: public or internal repository, renamed or transferred, inaccessible, `gh` missing or not authenticated, invalid or inconsistent response, several push URLs, other host, other repository, any other URL form (the refusal names the host that Git would contact). `export-plan` (offline) announces the check; `export-diff` performs it and presents the effective repository, observed visibility and UTC date (`ok: false` if `publish` would refuse); `publish --yes` redoes it last before any write in the clone (a refusal writes nothing) and re-reads the push URL just before `git push`. A `private` declaration, an earlier result or a confirmation never replaces it. Limitation: the visibility may change between the check and the send (only the local copy and commit separate them), without atomic guarantee with GitHub. The displayed URLs never carry credentials; a part that Git does not read as credentials (host followed by `#` or `?`) is never masked.
- Imported licence "to analyse" (C-19): the entire export of the product is refused until the exact licence is recorded (`license confirm --license-id`).
- Original legal documents of an imported script (2026-11-14): the export sends as is (name, bytes, encoding, language) the documents declared by the holder (`license confirm --license-document <path>` repeated, or `--no-license-documents`); it refuses the entire export, with the resolution, as long as the documents are not declared, a found file with a legal name (`LICENSE`, `COPYING`, `NOTICE`, `COPYRIGHT` and variants at the root or under `release/`, any file under `LICENSES/`) is not declared, or a declared document is missing, modified since the plan, a link, a special file, empty, binary, carries PWS template syntax or, towards a public destination, code of a closed source. The SPDX identifier alone does not say which documents the redistribution requires.
- `destination-remove` and the replacement of a destination of the same name invalidate its states: plans renamed `PLAN.invalidated.json`, clean clone set aside under `clones/.stale/`, clone carrying unpublished work marked `clones/<name>.STALE.json` and refused — never any deletion.
- Excluded from any export: symbolic links and special files (never followed), drafts (template `{{KEY}}` or unrendered conditional block), `terms_ref` that does not designate a recognized terms document of `release/`, terms document that no longer matches its current rendering, two files under the same target name (the plan is then refused).

## Local Git

- Local-first: commit only on explicit decision of the holder (`git commit` triggers a confirmation); `git push` under confirmation; `gh` limited to `auth status`, `repo view` (read) and `auth login` / `repo create` on confirmation.
- Git missing or folder not initialized: degraded mode flagged by the diagnostic (no local history, no worktrees); everything else works.
- Worktrees: useful for a risky piece of work; `.claude/settings.local.json` and `pws.config.json` are copied into them (`.worktreeinclude`) — they are COPIES.
- **Backup (recommended, not imposed)**: local Git on the same disk is not a hardware backup. Options: local bare repo, external disk, NAS. The local archives of `docs/maintenance/archives/` do not stand in for it.

## Permissions (Claude Code)

The shared rules of `.claude/settings.json` add confirmations; they never grant a general authorization. Since 2.2.0, PWS no longer imposes a systematic confirmation on local commits, local builds (`build-distribution`, `build-release`), update searches (`update check`, `pinets check-update`) and update downloads prepared locally without application (`update fetch`); Git and GitHub readings (`git remote -v`, `git tag`, `gh release view`, `gh release list`) are allowed. Explicit ask rules remain for the main publication, deletion, restoration, installation and update-application commands (`git push`, remote changes, tag deletion or forced replacement, `gh release create|edit|upload|delete`, `github publish`, `update apply`, `upgrade`, `migrate --apply|--rollback`, `pinets install|rollback`, archive removal, licence writes…), and the deny rules are unchanged.

- Removing an ask rule only lets Claude Code's normal mechanism decide: in auto mode its classifier may still ask for confirmation or refuse.
- The rules match the command text they recognize; they do not guarantee a confirmation for every possible variant (for example `git -C <dir> remote add` or `gh -R <repo> release create`).
- A technical permission never replaces the authorization of the mission: publishing still requires the holder's explicit agreement in the workflows concerned (`pine-github`, `pine-release`, the core release procedure).
- Personal settings (`.claude/settings.local.json`, `~/.claude/settings.json`) and managed settings may change the result; an ask or deny rule from any of them still applies, and an allow rule never outranks an ask rule.

## Public distribution and core upgrade

`python3 -m tools.pws_workspace build-distribution --target "<folder outside the workspace>"` builds the distribution from the common core (allowlist; products, `docs/maintenance`, runtime, personal configuration and bootstrap evidence excluded; post-copy check of personal data in three distinct families: absolute personal paths of any account (`/Users/<x>/`, `/home/<x>/`, `X:\Users\<x>\`), explicit traces of the system account that builds (only in a personal context: complete path component, `~<account>`, `<account>@host`, `USER=` assignment; never the bare word, so that a common account name such as `agent` does not flag the ordinary mentions of this word), identity configured in the workspace (holder and aliases, searched everywhere); core manifest `PWS_DISTRIBUTION.json`; target compared with the source by physical identity (case, link, `..`); a previous build is replaced with `--force` only if, apart from the files listed by its marker, it contains only `*.pyc` files of a `__pycache__/` under `tools/` (any other file: refusal, or old tree kept and flagged); `docs/licensing/LICENSING.md` and `tools/pine_exec/LICENSE` must be tracked by Git; files shipped as 0644, 0755 if they are executable). User-side installation: `install.py` / `INSTALL.md`. Upgrade of an existing installation: `upgrade --from <package> --plan|--apply` then `migrate`; rollback `migrate --rollback` then `upgrade --rollback` (`MIGRATION.md`). macOS first; Windows deferred; Linux not verified.

## Update Pine-Workspace (guided path, 2026-11-08, continuous since 2.2.0)

Since 2.2.0 Claude Code chains the steps below with `update guide --stage state`, `--stage search`, `--stage prepare` (download and verification of the release found, or `--package <zip or folder> [--sha256 <hash>]` for a local package, then the plan, in one step) and, after the single confirmation, `--stage apply --plan-file <plan> --yes`. Each stage returns a short summary in the configured language (what will change, what is kept with the `.pws-new` files to merge, the planned checks, the result, the remaining action and the recovery). The plan is bound to the installation, to the package files and to the origin, provenance and archive of the package: any change after the approval refuses the application, nothing changed. The release notes are classified available / absent / unusable; a summary in the configured language is drawn only from their text. The individual subcommands below stay available for advanced use.

In an installation that comes from a distribution (core manifest present):

1. `/pws → Maintenance / configuration → Outils et mises à jour → Mettre à jour Pine-Workspace` (in English: Maintenance / configuration → Tools and updates → Update Pine-Workspace): the state screen gives the installed version, the installation type and the last search ("not searched" as long as none has been made; otherwise the date and the result).
2. "Search for a new version" explicitly queries the stable releases of the official repository (`update check`); a network error or the absence of a release is displayed as such, never as "up to date"; pre-releases are not offered by default.
3. "View changes and limitations" displays the notes of the release found (or the `CHANGELOG.md` entry of the package).
4. "Prepare from the official release" downloads and verifies the release in a temporary folder outside the installation (`update fetch`: official repository and tag, `RELEASE.json`, SHA-256 hash, confined extraction, manifest), then computes the plan (`update plan`).
   **Offline**, "Prepare from a local package" verifies the integrity of an already downloaded archive or folder (`update prepare --package <zip or folder> [--sha256 <hash>]`); the origin is then not verified online, and the guided path says so.
5. The summary (versions, origin, changes, conflicts, files kept locally, possible migrations, backups, restart of Claude Code, non-atomicity) precedes a single "Apply / Cancel" confirmation; `update apply --plan-file <plan> --yes` runs `upgrade`, then `migrate` through the new code if all the steps appear in the plan, then verifies the files and runs the doctor. Quit and restart Claude Code afterwards.

Conflicting customization (core file modified locally): the plan lists it and the guided path stops without overwriting anything (never an automatic `--overwrite-local`). Either: put the file back in its shipped state (or keep a copy of it outside the core) then plan again; or, knowingly, `upgrade --from <package> --apply --overwrite-local` on the command line (the file is backed up first). The locally mutable core files (`PROVENANCE.json`, calibration, pin and lockfile, `.claude/settings.json`) are kept and the new version is written next to them as `.pws-new`.

Rollback: "Rollback" (`update rollback-info`) lists the backups and the order — data first (`migrate --rollback <stamp>`), code next (`upgrade --rollback <stamp>`, refused as long as a later migration is recorded) — according to the guarantees of `MIGRATION.md`; nothing is restored without an explicit command.

Why not a reinstallation over the existing one: `install.py` copies an entire package into an empty folder; it compares nothing, backs up nothing and would overwrite the customizations; it therefore refuses an existing installation. Only `upgrade` compares each file with the installed core manifest, keeps the mutable files, backs up, and allows rollback.

The original installation (development upstream, no core manifest) can consult the releases, but no public distribution applies to it: it evolves through its own repository.

## Preparing a core release (maintainer, 2026-11-08)

1. Choose the number according to the MAJOR.MINOR.PATCH convention (`MIGRATION.md`); a published version is never replaced: a fix takes a new number. Set `WORKSPACE_VERSION` in `tools/pws_workspace/version.py`, then add the entry `## [x.y.z] — … (date)` at the top of `CHANGELOG.md` (changes, prerequisites, limitations); `doctor` (check `version-sources`) and the targeted tests must pass; commit.
2. `python3 -m tools.pws_workspace build-release --target "<folder outside the workspace>"`: builds the distribution through the existing mechanism, then `pine-workspace-x.y.z.zip`, `pine-workspace-x.y.z.zip.sha256`, `RELEASE.json`, `RELEASE_NOTES.md`, and verifies them (refusal if the CHANGELOG number differs, if an archive with the same number already exists, or if the target is inside the source or contains it — physical identity; archive entries as 0644/0755; no private content, no Git history).
3. Check that the tag does not exist yet (`git ls-remote --tags <official repository URL>`), then, with the explicit agreement of the holder: tag `vx.y.z` on the published commit, GitHub release with the four assets (exact names) and the notes. None of this is executed by the tool.
4. Check after publication: `update check` from a test installation finds the version, `update fetch` verifies the hash and the manifest, `update plan` then `update apply` succeed on a temporary installation. The published hash guarantees integrity, not authenticity (no signature is in place).
