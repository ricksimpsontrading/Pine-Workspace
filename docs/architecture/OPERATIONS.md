# OPERATIONS — procédures récurrentes

Document humain concis. Les règles de développement Pine vivent dans `standards/PINE_SCRIPT_V6_STANDARD.md` ; les workflows détaillés dans `.claude/skills/` ; l'installation dans `INSTALL.md` ; les migrations dans `MIGRATION.md`.

## Lancement

Pine Workspace est autonome : aucun projet sibling requis. Toujours lancer depuis sa propre racine physique (chemin libre, espaces admis) :

```bash
cd "<dossier du workspace>"
claude                      # session normale — l'état PWS s'affiche au démarrage (langue configurée)
/pws                        # menu guidé : action d'abord, script ensuite
```

Un resume, un compact ou un clear ne rouvre pas le menu automatiquement. Au lancement, l'entretien déterministe (liste blanche : fichiers `*.pyc` rangés directement dans un `__pycache__/` sous `tools/`, `.DS_Store`, instantanés de session au format du hook inutilisés depuis 7 jours — date de dernière utilisation, rafraîchie par le hook Stop à chaque fin de tour —, jamais celui de la session courante ni celui de `latest.json` ; tout élément cité par un fichier texte suivi par Git est conservé) s'exécute et ne se signale que s'il a agi.

## Configuration personnelle (`pws.config.json`)

```bash
python3 -m tools.pws_workspace init --language fr|en [--copyright-holder "…"] [--alias "…"]   # première fois
python3 -m tools.pws_workspace config show
python3 -m tools.pws_workspace config set language en
python3 -m tools.pws_workspace config set identity.copyright_holder "…"
python3 -m tools.pws_workspace config set maintenance.startup_cleanup false
```

Séparée des réglages de Claude Code (`.claude/settings*.json` : permissions et approbations uniquement). Non versionnée, copiée dans les worktrees. Sans fichier : anglais, mode TradingView `manual`, identité non configurée (contrôles de copyright UNVERIFIABLE, jamais bloquants).

## Gestes courants

- **Ajouter un `.pine` existant** : créer `scripts/<slug>/`, y déposer le fichier ; il sera détecté UNREGISTERED (SessionStart ou doctor) et onboardé via `pine-onboard` (`/pws → Nouveau / importer → Importer`).
- **Nouveau produit** : décrire l'objectif ou `/pws → Nouveau script` → `pine-new` (type, puis profil FREE / FREE à source fermé / PRIVATE / COMMERCIAL).
- **Diagnostic** : `python3 -m tools.pws_workspace doctor` (BLOCKING = actionnable ; INFO = limitation déclarée ; ne répare jamais).
- **État compact** : `python3 -m tools.pws_workspace session-status` ; **menu** : `menu --json` (son champ `banner` porte la bannière **fixe** « Pine-WS » du menu, FIGlet Standard, 41 colonnes, et `banner.question`, texte complet de la question du menu principal transmis tel quel par `/pws` ; aucune adaptation à la largeur).
- **Bannière dans un terminal** (usage distinct de la bannière du menu) : `python3 -m tools.pws_workspace banner` (variantes adaptatives PINE-WORKSPACE : large, compacte ou texte brut selon la largeur du terminal mesurée à chaque affichage ; `--json` : forme structurée). Purement visuelle : aucune sortie JSON ni aucun hook n'en est préfixé.
- **Mettre à jour Pine-Workspace** : `/pws → Maintenance / configuration → Outils et mises à jour → Mettre à jour Pine-Workspace` (section dédiée ci-dessous).
- **Tests du tooling** : `python3 -m unittest discover -s tools/tests -t .` (depuis la racine).
- **Licences** : parcours guidé `/pws → Qualité / publication → Licence et conditions d'utilisation` (`pine-license`, indépendant de la publication) ; `license overview --slug <slug>` (état consolidé, lecture seule) ; `license status --slug <slug>` ; `license preview|render --slug <slug> --kind header-free|header-proprietary|notice|grant|eula` (aperçu, rien d'écrit) ; `license set-fields --slug <slug> --field NAME=valeur … [--clear NAME] [--dry-run]` (champs du titulaire dans `release/eula-fields.json`, valeurs existantes conservées) ; `license write --slug <slug> --kind <kind>` (→ `release/EULA.md`, `release/FREE_USE_GRANT.md`, `release/NOTICE.md`, `release/HEADER_*.txt` ; brouillon tant que des champs indispensables manquent) ; `license confirm --slug <slug> [--state …] [--privacy …] [--mode …] [--created-year …] [--terms-ref <chemin>] [--terms-url <https>]` (faits confirmés dans le manifeste).

## Lire les statuts

- `product_structure_status` : `REGISTERED` / `INCOMPLETE` / `BROKEN` / `AMBIGUOUS`. La valeur synthétique n'écrase jamais la liste détaillée des findings. Un manifeste schéma 1 reste lu (profil dérivé, finding `MANIFEST_LEGACY_SCHEMA`) jusqu'à `migrate --apply`.
- `profile` / `license` : FREE | PRIVATE | COMMERCIAL et les cinq axes ; `EULA_DRAFT` et `ACCESS_PAID_WITHOUT_EULA` sont des avertissements (jamais bloquants pour le développement, à régler avant une publication commerciale).
- `source_registration_status` : `REGISTERED` / `UNREGISTERED` (orphelin → onboarding requis avant édition substantielle).
- Validation TradingView : persisté ∈ `unverified / in-progress / passed / failed / partial` ; `stale` est DÉRIVÉ ; intégrité `BROKEN` → jamais `passed`.

## Mode TradingView

- Mode courant : `python3 -m tools.pws_workspace tv-mode` (configuration ; source `config`, `legacy` ou `default`). Un choix fait par `tv-mode <mode>` enregistre sa provenance (`tv_validation_mode_choice`) : c'est ce choix qui résout un conflit avec une valeur héritée signalé par `migrate --plan` (m001 bloquée, jamais résolue d'office).
- Changement (réservé au titulaire) : `/tv-mode manual` ou `/tv-mode chrome-experimental`, ou `/pws → Maintenance / configuration → Configuration → Mode TradingView`. Même contrôleur atomique (verrou de `pws.config.json`, refus de conflit). `manual` reste le défaut ; `chrome-experimental` reste explicitement optionnel.
- **Validation manuelle** : `tv-validate` prépare la matrice adaptée au changement ; le titulaire exécute dans TradingView et rapporte ses observations réelles ; le run est lié au SHA-256 du source.
- **Validation chrome-experimental** : nécessite `claude --chrome` et l'extension connectée. Tout cas ambigu → fallback manuel du run, mode persistant inchangé. Publication toujours exclue.

## Niveaux de vérification

1. Travail courant (`pine-develop`) : lecture ciblée, diff, guard ; PineTS seulement si prévu.
2. Audit approfondi (`pine-audit`) : explicite, périmètre annoncé (lecture globale, cartographe, reviewer, PineTS si inclus).
3. Préparation de publication (`pine-release`) : couverture globale consolidée unique, revue de release, règles TradingView revérifiées, validation du SHA final.

Guard (`python3 -m tools.pws_workspace guard "scripts/<slug>"`, mêmes règles que le hook Stop) : le manifeste est lu après validation (manifeste BROKEN = `manifest` BLOCKING) ; mention et URL CC contrôlées exactement, la ligne © nomme le titulaire ; un champ de modèle non rendu (`{{YEAR_RANGE}}`…) bloque ; BOM toléré ; URL de licence d'une notice tierce admise par une règle ciblée (URL de licence reconnue — http compris, CC0, SPDX, fichier LICENSE d'un dépôt sur un hébergeur connu — dans une ligne de commentaire de notice), jamais par une exemption générale : une URL promotionnelle reste bloquante ; un en-tête portant une autre licence que le manifeste bloque avec un libellé de décision du titulaire (licence à analyser, ne jamais retirer ni remplacer une notice existante) ; une notice tierce à côté des mentions déclarées, des mentions contradictoires (`header-consistency`) ou un contact promotionnel (`no-promo-contacts`) donnent un avertissement.

## Outils intégrés (PineTS)

- État : `tooling-status` (Node/npm, pin, lockfile, version installée, SHA de l'artefact installé, provenance, calibration, points de retour avec leur utilisabilité, dernière recherche de mise à jour datée). Trois informations distinctes : l'état local (installé, intégrité, calibration), la disponibilité d'une mise à jour (uniquement d'après une recherche explicite enregistrée, avec sa date ; sans recherche, elle est inconnue — jamais « à jour » par défaut) et les points de retour utilisables.
- Vérification : `pinets verify` (`--record` enregistre une première fois le SHA de l'artefact dans `PROVENANCE.json`) ; contrôle aussi `PROVENANCE.pinned_version` = pin et les restes d'un retour arrière interrompu (WARNING) ; mêmes gravités que le doctor : artefact différent BLOCKING, artefact absent avec `node_modules` WARNING, moteur absent INFO. `tooling-status` lit l'intégrité à chaque appel (`artifact_check`) ; `provenance_verified_at` est la date consignée dans `PROVENANCE.json`, jamais une vérification faite sur cette machine ; la fraîcheur n'est jamais CURRENT pour un moteur absent ou un artefact différent.
- Mise à jour : `pinets check-update` (réseau explicite, n'installe rien ; résultat daté enregistré dans `.claude/runtime/tooling/last-update-check.json`) → `pinets install <version> --yes` (point de retour, `npm install --save-exact --ignore-scripts`, `npm ci --ignore-scripts`, contrôle du moteur obtenu — pin, lockfile et intégrité, `node_modules/pinets`, artefact — avant toute écriture de la provenance et des calibrations STALE, sinon échec avec l'état et le point de retour) ; `check-update` compare numériquement au pin courant : seule une version stable strictement plus récente est une mise à jour, toute réponse sans version exacte exploitable est une erreur et rien n'est enregistré → `pinets recalibrate-plan` (plan en lecture seule ; la recalibration elle-même est manuelle et revue) → `pinets verify` → tests.
- Retour arrière : `pinets rollback <version> --yes` — restauration en deux temps d'un point de retour **utilisable** de `.claude/runtime/pinets-rollback/<version>/`. Utilisable = manifeste `ROLLBACK_MANIFEST.json` au format courant (2 : empreinte SHA-256 de chaque fichier du moteur et de l'arbre `node_modules` entier, liens symboliques enregistrés avec leur cible), complet et vérifié sur le contenu sauvegardé (chemins confinés, rien d'inconnu dans l'arbre). Premier temps, sous le verrou partagé avec `upgrade`/`migrate` : validation complète du point, sauvegarde vérifiée du moteur courant (`before-rollback-<horodatage>`), copie préparée à côté du moteur et vérifiée — une seule anomalie refuse tout, le moteur actif n'est pas modifié (`stage: refused`). Second temps : renommages atomiques puis vérification finale du moteur actif (fichiers, arbre complet, artefact) ; succès déclaré seulement vérifié (`stage: verified`) ; une erreur après le premier renommage est signalée `incomplete` avec les éléments de récupération conservés (point, point pré-retour, arbres `.restore-*` et `node_modules.replaced-*`). Un point disposé à la main (par exemple le 0.9.33 avec ses fichiers sous `tracked/`) ou au format 1 (noms de fichiers et empreinte de l'artefact seulement) est listé non utilisable avec sa raison, refusé par la commande, jamais converti en recalculant les empreintes de son contenu actuel : procédure manuelle documentée. `pinets install` refuse de démarrer sans point vérifié du moteur courant ; un ancien point de même version est conservé tel quel et un nouveau point horodaté est créé à côté. Retour par défaut : le point réellement sauvegardé par la dernière installation (`previous_pin.rollback_point`), sinon le plus récent point utilisable sauvegardé par une installation pour le pin précédent, jamais un `before-rollback-*`. Refus si `.claude/runtime/pinets-rollback` ou un parent est un lien symbolique ou sort du workspace. Une interruption (Ctrl-C) avant les renommages rend `refused`, pendant `incomplete` ; les restes `.restore-*` et `node_modules.replaced-*` sont signalés par `verify`, le doctor et `tooling-status`, jamais supprimés automatiquement.
- Interpréter honnêtement : `PINETS_EXECUTION_PASS` ≠ validé TradingView ; aucune modification d'un indicateur pour satisfaire une divergence du moteur.
- Non installés, place documentée seulement : `pinets-cli`, Vela, edge-stats, LuxAlgo MCP.

## Archives et nettoyage

- Entretien : `maintenance cleanup` (plan) / `--execute` ; liste blanche uniquement ; journal `.claude/runtime/maintenance/cleanup-log.jsonl`.
- Import d'archives externes : `archives-plan` → `archives-import` → `archives-verify` → `archives-remove-source`. Relations refusées à chaque étape, par identité physique : source égale au workspace, dedans ou le contenant, source dans une autre installation PWS ou la contenant, source donnée par un lien symbolique, cible hors de `docs/maintenance/archives`. La suppression refait l'inventaire du contenu ACTUEL du dossier externe et refuse tout fichier nouveau, modifié ou non vérifiable ; elle ne supprime, fichier par fichier, que ce qui vient d'être vérifié comme archivé, puis les dossiers vidés — jamais de suppression récursive. Un plan périmé (dossier recréé ou contenu changé) est refusé. Index cumulatif : `docs/maintenance/archives/INDEX.md`, `MANIFEST.json`. Les anciens rapports gardent leurs chemins d'origine.
- Quatre notions à ne pas confondre pour `docs/maintenance/archives/` : (1) **stockage local** — les fichiers vivent dans l'arbre du workspace ; (2) **suivi par Git** — ils ne sont pas ignorés (`.gitignore` ne doit jamais exclure une archive ni une preuve, FILE_CONTRACTS) et seront suivis au prochain commit décidé par le titulaire ; le poids (211 Mo de fichiers binaires) est une conséquence acceptée du choix de les versionner, toute autre politique (Git LFS, dépôt séparé) est une décision distincte à prendre avant commit, jamais un `.gitignore` ajouté en silence ; (3) **sauvegarde indépendante du disque** — ni le dossier local ni Git local n'en tiennent lieu ; (4) **exclusion de la distribution publique** — `docs/maintenance/` n'est jamais livré (`build-distribution`).

## GitHub

- Connexion : `github status` (gh ou credential helper ; aucun jeton affiché ni stocké ; le credential helper n'est montré que par son nom, un assistant en ligne (`!…`) ou une valeur portant un mot de passe ou un jeton est masqué). Établir la connexion soi-même (`! gh auth login`).
- Destinations : `github destinations`, `destination-add --name … --repo owner/name --visibility public|private [--path-prefix …]`.
- Export : `github export-plan --slug <slug> --destination <name>` (inclus / exclus / staging) → `github fetch --destination <name>` (clone local, réseau explicite) → `github export-diff` → `github publish … --yes` (seulement après autorisation explicite ; `git push` reste soumis à confirmation).
- Un source `closed` n'est jamais exporté vers une destination `public`, ni directement ni par une copie, un lien ou un document qui reproduit son code.
- Le plan (`PLAN.json`, format 2) est lié à la destination effective (nom, dépôt, visibilité, branche, préfixe, URL), à la licence et à l'empreinte de chaque fichier : `export-diff` et `publish` relisent la configuration et le manifeste, recalculent le plan et refusent tout écart (action : refaire `export-plan`). Le clone local doit avoir pour `origin` l'URL configurée, la bonne branche et aucun travail non publié, sinon refus (action : `fetch` ou examen du clone). Le push vise explicitement la branche configurée.
- Identité de la destination pour **tout** envoi (demande du titulaire du 2026-11-14), contenu public compris : `export-diff` (présenté dans `destination_check`) et `publish --yes` (refait juste avant toute écriture dans le clone) refusent quand le remote du clone n'a pas une seule URL de fetch et une seule URL de push telles que Git les utilise (`pushurl`, `insteadOf`, `pushInsteadOf` appliqués, configuration globale comprise), ou quand ces URL et celle de la destination ne désignent pas, sous les formes strictes ci-dessous, le dépôt configuré. Même et unique contrôle du remote que pour un source fermé ; GitHub n'est pas interrogé pour un contenu public, qui peut aller vers une destination publique ou vers un dépôt privé choisi explicitement. `publish` relit le remote juste avant `git push` : s'il a changé après le commit local, rien n'est poussé et `state_left` décrit l'état laissé sur disque (clone, branche, commit, fichiers écrits, travail non publié, plan conservé, étapes suivantes) ; le titulaire inspecte et abandonne lui-même ce commit avant un nouveau `fetch`. Sont aussi refusés : une entrée d'URL vide ; un réglage qui fait se connecter Git ailleurs que l'URL affichée ou sans la vérifier (`core.sshCommand`, `core.gitProxy`, `remote.origin.vcs`, `http.curloptResolve`, `http.sslVerify` à faux, variables `GIT_SSH`, `GIT_SSH_COMMAND`, `GIT_PROXY_COMMAND`, `GIT_SSL_NO_VERIFY`) ; une cible qui ne diffère que par la casse d'une entrée du dépôt ou qui exige un dossier là où il a un fichier ; un fichier dont Git modifierait les octets au commit (`.gitattributes`, `core.autocrlf`, filtres). Aucun hook ne s'exécute lors du commit et du push du clone ; le commit est vérifié avant le push (un seul nouveau commit, seulement les chemins du plan, octets exacts). Limites : un changement fait dans l'instant entre la dernière lecture et le push lui-même n'est pas détecté ; le contrôle hors ligne ne voit ni un dépôt renommé ou transféré sur GitHub, ni `~/.ssh/config`, ni un environnement compromis.
- Source fermé (I-06, décision du titulaire du 2026-11-13) : un envoi qui contient un source fermé (source du produit dont `source_visibility` n'est pas `public`, source public qui reproduit le source fermé d'un autre produit, ou document portant du code Pine d'un source fermé ; manifestes relus au moment de l'envoi) exige que le remote du clone ait une seule URL de fetch et une seule URL de push telles que Git les utilise (`pushurl`, `insteadOf`, `pushInsteadOf` appliqués), toutes deux — comme l'URL de la destination — écrites exactement sous l'une des formes `https://github.com/<owner>/<repo>[.git][/]`, `git@github.com:<owner>/<repo>[.git]`, `ssh://git@github.com/<owner>/<repo>[.git]` (sans identifiants ni autre partie utilisateur, port, requête, fragment ni encodage `%`) et désignant le dépôt configuré, puis que `gh repo view https://github.com/<owner>/<repo> --json nameWithOwner,visibility,isPrivate,url` (authentification `gh` courante, jamais `gh api`) rapporte ce dépôt lui-même comme `PRIVATE` (`isPrivate: true`). Sinon refus : dépôt public ou interne, renommé ou transféré, inaccessible, `gh` absent ou non authentifié, réponse invalide ou incohérente, plusieurs URL de push, autre hôte, autre dépôt, toute autre forme d'URL (le refus nomme l'hôte que Git contacterait). `export-plan` (hors ligne) annonce le contrôle ; `export-diff` l'effectue et présente dépôt effectif, visibilité observée et date UTC (`ok: false` si `publish` refuserait) ; `publish --yes` le refait en dernier avant toute écriture dans le clone (un refus n'écrit rien) et relit l'URL de push juste avant `git push`. Une déclaration `private`, un résultat antérieur ou une confirmation ne le remplacent jamais. Limite : la visibilité peut changer entre le contrôle et l'envoi (seules la copie et le commit locaux les séparent), sans garantie atomique avec GitHub. Les URL affichées ne portent jamais d'identifiants ; une partie que Git ne lit pas comme des identifiants (hôte suivi de `#` ou `?`) n'est jamais masquée.
- Licence importée « à analyser » (C-19) : l'export entier du produit est refusé jusqu'à l'enregistrement de la licence exacte (`license confirm --license-id`).
- Documents juridiques d'origine d'un script importé (2026-11-14) : l'export envoie à l'identique (nom, octets, encodage, langue) les documents déclarés par le titulaire (`license confirm --license-document <chemin>` répété, ou `--no-license-documents`) ; il refuse l'export entier, avec la résolution, tant que les documents ne sont pas déclarés, qu'un fichier de nom juridique trouvé (`LICENSE`, `COPYING`, `NOTICE`, `COPYRIGHT` et variantes à la racine ou sous `release/`, tout fichier sous `LICENSES/`) n'est pas déclaré, ou qu'un document déclaré est absent, modifié depuis le plan, lien, fichier spécial, vide, binaire, porte une syntaxe de modèle PWS ou, vers une destination publique, du code d'un source fermé. L'identifiant SPDX ne dit pas à lui seul quels documents la redistribution exige.
- `destination-remove` et le remplacement d'une destination de même nom invalident ses états : plans renommés `PLAN.invalidated.json`, clone propre mis de côté sous `clones/.stale/`, clone portant du travail non publié marqué `clones/<nom>.STALE.json` et refusé — jamais de suppression.
- Exclus de tout export : liens symboliques et fichiers spéciaux (jamais suivis), brouillons (`{{CLÉ}}` de modèle ou bloc conditionnel non rendu), `terms_ref` qui ne désigne pas un document de conditions reconnu de `release/`, document de conditions qui ne correspond plus à son rendu actuel, deux fichiers sous le même nom cible (le plan est alors refusé).

## Git local

- Local-first : commit uniquement sur décision explicite du titulaire (`git commit` déclenche une confirmation) ; `git push` en confirmation ; `gh` limité à `auth status`, `repo view` (lecture) et `auth login` / `repo create` sur confirmation.
- Git absent ou dossier non initialisé : mode dégradé signalé par le diagnostic (pas d'historique local, pas de worktrees) ; tout le reste fonctionne.
- Worktrees : utiles pour un chantier risqué ; `.claude/settings.local.json` et `pws.config.json` y sont copiés (`.worktreeinclude`) — ce sont des COPIES.
- **Backup (recommandé, non imposé)** : Git local sur le même disque n'est pas un backup matériel. Options : repo bare local, disque externe, NAS. Les archives locales de `docs/maintenance/archives/` n'en tiennent pas lieu.

## Distribution publique et mise à niveau du cœur

`python3 -m tools.pws_workspace build-distribution --target "<dossier hors du workspace>"` construit la distribution à partir du cœur commun (liste blanche ; produits, `docs/maintenance`, runtime, configuration personnelle et preuves de bootstrap exclus ; contrôle post-copie des données personnelles en trois familles distinctes : chemins personnels absolus de tout compte (`/Users/<x>/`, `/home/<x>/`, `X:\Users\<x>\`), traces explicites du compte système qui construit (seulement en contexte personnel : composant de chemin complet, `~<compte>`, `<compte>@hôte`, affectation `USER=` ; jamais le simple mot, pour qu'un nom de compte courant tel que `agent` ne signale pas les mentions ordinaires de ce mot), identité configurée dans le workspace (titulaire et alias, cherchés partout) ; manifeste de cœur `PWS_DISTRIBUTION.json` ; cible comparée à la source par identité physique (casse, lien, `..`) ; une construction précédente n'est remplacée avec `--force` que si, hors fichiers listés par son marqueur, elle ne contient que des `*.pyc` d'un `__pycache__/` sous `tools/` (tout autre fichier : refus, ou ancien arbre conservé et signalé) ; `docs/licensing/LICENSING.md` et `tools/pine_exec/LICENSE` doivent être suivis par Git ; fichiers livrés en 0644, 0755 s'ils sont exécutables). Installation côté utilisateur : `install.py` / `INSTALL.md`. Mise à niveau d'une installation existante : `upgrade --from <paquet> --plan|--apply` puis `migrate` ; retour arrière `migrate --rollback` puis `upgrade --rollback` (`MIGRATION.md`). macOS d'abord ; Windows différé ; Linux non vérifié.

## Mettre à jour Pine-Workspace (parcours guidé, 2026-11-08)

Dans une installation issue d'une distribution (manifeste de cœur présent) :

1. `/pws → Maintenance / configuration → Outils et mises à jour → Mettre à jour Pine-Workspace` : l'écran d'état donne la version installée, le type d'installation et la dernière recherche (« non recherchée » tant qu'aucune n'a été faite ; sinon la date et le résultat).
2. « Rechercher une nouvelle version » interroge explicitement les releases stables du dépôt officiel (`update check`) ; une erreur réseau ou une absence de release est affichée telle quelle, jamais comme « à jour » ; les préversions ne sont pas proposées par défaut.
3. « Consulter les changements et limites » affiche les notes de la release trouvée (ou l'entrée de `CHANGELOG.md` du paquet).
4. « Préparer depuis la release officielle » télécharge et vérifie la release dans un dossier temporaire hors de l'installation (`update fetch` : dépôt et tag officiels, `RELEASE.json`, empreinte SHA-256, extraction confinée, manifeste), puis calcule le plan (`update plan`).
   **Hors ligne**, « Préparer depuis un paquet local » vérifie l'intégrité d'une archive ou d'un dossier déjà téléchargés (`update prepare --package <zip ou dossier> [--sha256 <empreinte>]`) ; l'origine n'est alors pas vérifiée en ligne, et le parcours le dit.
5. Le récapitulatif (versions, origine, changements, conflits, fichiers conservés localement, migrations possibles, sauvegardes, relance de Claude Code, non-atomicité) précède une seule confirmation « Appliquer / Annuler » ; `update apply --plan-file <plan> --yes` exécute `upgrade`, puis `migrate` par le nouveau code si toutes les étapes figurent dans le plan, puis vérifie les fichiers et lance le doctor. Quitter et relancer Claude Code ensuite.

Personnalisation en conflit (fichier du cœur modifié localement) : le plan la liste et le parcours s'arrête sans rien écraser (jamais `--overwrite-local` automatique). Au choix : remettre le fichier dans son état livré (ou en garder une copie hors du cœur) puis replanifier ; ou, en connaissance de cause, `upgrade --from <paquet> --apply --overwrite-local` en ligne de commande (le fichier est sauvegardé d'abord). Les fichiers de cœur localement mutables (`PROVENANCE.json`, calibration, pin et lockfile, `.claude/settings.json`) sont conservés et la nouvelle version est écrite à côté en `.pws-new`.

Retour arrière : « Retour arrière » (`update rollback-info`) liste les sauvegardes et l'ordre — données d'abord (`migrate --rollback <stamp>`), code ensuite (`upgrade --rollback <stamp>`, refusé tant qu'une migration postérieure est enregistrée) — selon les garanties de `MIGRATION.md` ; rien n'est restauré sans une commande explicite.

Pourquoi pas une réinstallation par-dessus : `install.py` copie un paquet entier dans un dossier vide ; il ne compare rien, ne sauvegarde rien et écraserait les personnalisations ; il refuse donc une installation existante. Seul `upgrade` compare chaque fichier au manifeste de cœur installé, conserve les fichiers mutables, sauvegarde, et permet le retour arrière.

L'installation d'origine (amont de développement, aucun manifeste de cœur) peut consulter les releases, mais aucune distribution publique ne s'y applique : elle évolue par son propre dépôt.

## Préparer une release du cœur (mainteneur, 2026-11-08)

1. Choisir le numéro selon la convention MAJEURE.MINEURE.CORRECTIF (`MIGRATION.md`) ; une version publiée n'est jamais remplacée : une correction prend un nouveau numéro. Mettre `WORKSPACE_VERSION` dans `tools/pws_workspace/version.py`, puis ajouter l'entrée `## [x.y.z] — … (date)` en tête de `CHANGELOG.md` (changements, prérequis, limites) ; `doctor` (contrôle `version-sources`) et les tests ciblés doivent passer ; commiter.
2. `python3 -m tools.pws_workspace build-release --target "<dossier hors du workspace>"` : construit la distribution par le mécanisme existant, puis `pine-workspace-x.y.z.zip`, `pine-workspace-x.y.z.zip.sha256`, `RELEASE.json`, `RELEASE_NOTES.md`, et les vérifie (refus si le numéro du CHANGELOG diffère, si une archive du même numéro existe déjà, ou si la cible est dans la source ou la contient — identité physique ; entrées de l'archive en 0644/0755 ; aucun contenu privé, aucun historique Git).
3. Vérifier que le tag n'existe pas encore (`git ls-remote --tags <url du dépôt officiel>`), puis, sur accord explicite du titulaire : tag `vx.y.z` sur le commit publié, release GitHub avec les quatre actifs (noms exacts) et les notes. Rien de tout cela n'est exécuté par l'outil.
4. Contrôle après publication : `update check` depuis une installation d'essai trouve la version, `update fetch` vérifie l'empreinte et le manifeste, `update plan` puis `update apply` réussissent sur une installation temporaire. L'empreinte publiée garantit l'intégrité, pas l'authenticité (aucune signature n'est mise en place).
