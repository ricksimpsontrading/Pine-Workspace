# Modification d'un script onboardé

Langue : répondre dans la langue configurée (`language` de `session-status --json`) ; code et textes du produit en anglais.

## Séquence (spec §24.2, master §38 — niveaux de vérification du master §9.1)

1. Lire le contexte local requis (`CLAUDE.md` local, `PRODUCT.md`, `ARCHITECTURE.md`, `SCRIPT.json` : profil et axes de licence).
2. Comprendre précisément la demande ; classer la tâche (master §2 : correction locale / changement fonctionnel / structurel / release). Le niveau est le **travail courant** (cette skill) pour toute classe, y compris un changement structurel ; l'**audit approfondi** (`pine-audit`) n'a lieu que si le titulaire le demande (le proposer si le risque le justifie, ne jamais l'engager) ; la **préparation de publication** relève de `pine-release`.
3. Lire la cartographie (`ARCHITECTURE.md`) puis les blocs concernés et leurs dépendances pertinentes (producteurs, consommateurs, textes, visuels, alertes), étendues selon la classe : plus larges pour un changement structurel, jamais intégrales par défaut. Agent `pws-pine-cartographer` et lecture intégrale : seulement dans un audit demandé. Cartographie jugée fausse ou insuffisante : le signaler et proposer un audit.
4. Inventaire d'impact (master §10) : ce qui change, ce qui doit rester inchangé, consommateurs, textes/visuels/alertes dépendants. L'inventaire conclut explicitement sur la compilation minimale intermédiaire (spec §30.5) : « requise », avec le risque nommé (typage, profondeur d'historique, taille compilée), ou « non requise ».
5. Vérifier la documentation Pine actuelle pertinente ; vérification de pertinence du benchmark (master §8 — conclure `N/A` explicitement si rien d'utile) ; `pine-research` si nécessaire. Toute implémentation reste originale (master §8.5).
6. Définir la modification minimale cohérente ; planifier ; implémenter par unités cohérentes (master §11 — pas de scope creep : toute amélioration non demandée qui constitue une décision produit est proposée au titulaire d'abord). Aucun journal de travail dans les commentaires du source (master §24.5).
7. Relire selon la couverture du master §9.2 et contrôler le diff ; auto-revue sur les quatre axes du master §36 limitée au périmètre modifié ; synchroniser les artefacts dépendants (axe 2). Pour chaque affirmation significative modifiée ou déclarée vérifiée (tooltip, commentaire, conclusion de conformité), garder une référence courte au symbole ou au contrat qui la justifie et sa limite.
8. Revue indépendante (`pine-review` → `pws-pine-reviewer`) seulement dans un audit demandé, en préparation de publication ou à la demande du titulaire — jamais déclenchée par la classe de la tâche ; une fois, sans cascade.
9. `python3 -m tools.pws_workspace guard "scripts/<slug>"`.
10. `pine-local-test` seulement si l'inventaire d'impact l'a prévu — sauf dans une séance de test local déjà ouverte par le titulaire (script et données choisis) : le suivi y calcule chaque sauvegarde ; déclarer alors l'attente de l'inventaire pour la révision enregistrée AVANT d'examiner son résultat (`local-test expect --change … --unchanged … --note …`), puis interpréter `qualification` et `expectation_facts` (EXPECTED / UNEXPECTED / UNRESOLVED ; UNRESOLVED si les preuves ne tranchent pas). Hors séance : (construction touchée couverte par une capability, risque réel) : smoke run pour une petite correction, comparaison de régression pour un refactor neutre ; jamais par défaut après une petite modification.
10 bis. **Prochaine vérification utile (EXPÉRIMENTAL, consultatif)** — quand l'inventaire justifie un test local du changement :
   - Démarrer ou reprendre le suivi sur la copie de travail qui sera réellement modifiée : `local-test work --slug <slug> --dataset <données locales>` ; modifier `session.work_source` (jamais le source enregistré pendant la séance). Si une copie de travail existante diffère du source enregistré, le signaler avant de la reprendre.
   - **Modification de calcul (D2)** : après la sauvegarde, AVANT de lire le résultat, `local-test impact` donne pour chaque sortie (`plot`, `plotshape`, `hline`…) son statut et la chaîne de définitions qui le justifie : `may-change` (dépend, par des noms définis dans le source, d'une définition modifiée — par ex. `Overbought <- r (ligne 3 : ta.rsi(close, 14) -> ta.rsi(close, 21))`), `stays-identical` (ne dépend de rien de modifié — par ex. « constant 70 »), `uncertain` (construction non suivie : bloc, boucle, fonction, tuple, titre non littéral). L'expliquer au titulaire sans en dire plus que la chaîne : un nom de série ou une valeur égale ne suffit jamais ; `may-change` n'est pas « changera ». Puis `local-test expect --from-impact --note "<inventaire>"` lie ces prévisions par sortie à la révision enregistrée. **Présenter alors la prévision au titulaire dans un message à part, AVANT d'appeler `next` ou `inspect`** : `expectation.explanation` donne, pour chaque sortie, son statut et sa raison (la chaîne de définitions, ou « constante ») ; rappeler que « peut changer » n'est pas « changera ». Si le titulaire demande d'expliquer avant de lire, s'arrêter après cette présentation et lire le résultat à sa demande. Seulement ensuite, lire le résultat. `next` rend alors `outputs_observed` (ce que chaque sortie a fait face à sa prévision) ; une sortie prévue identique qui diffère donne `read-bar` à sa première barre établie ; une sortie `may-change` restée identique sur les bougies testées n'est pas une anomalie.
   - Après chaque sauvegarde, AVANT d'en lire le résultat : `local-test expect --change <facettes> --unchanged <facettes> --note "<inventaire>"` (facettes : values, signals, objects, styles ; une modification « esthétique » → `--change styles --unchanged values,signals,objects`). L'attente est liée à la révision enregistrée.
   - Demander la prochaine vérification : `local-test next --wait 120`. PWS lit seulement ses fichiers (zéro appel à PineTS) et rend `next_check` :
     - `none` : seul le changement attendu est observé ; aucun contrôle supplémentaire ne se justifie sur les éléments comparés (dire aussi `not_covered`) ;
     - `read-bar` : un signal (ou une valeur) diffère alors qu'il devait rester inchangé ; série, barre de la première divergence établie, ce que chaque run y rapporte (`at_bar`), les deux runs et la commande de relecture. L'exécuter (`local-test inspect --run-id <résultat> --bar N --compare-run-id <référence>` : `chart_values` donne les valeurs de l'annexe, booléens des signaux compris) et expliquer l'écart au titulaire ;
     - `unverifiable` : l'annexe d'un des deux runs (ou des deux) manque ou est refusée — `unavailable_annexes` donne le run, son rôle (référence ou résultat) et la raison exacte ; les signaux nommés le sont seulement d'après une annexe valide, aucune barre n'est désignée, `numeric_facts` garde à part ce que les rapports établissent. Dire explicitement que ces signaux et styles sont invérifiables, jamais inchangés ;
     - `not-comparable` : les deux runs ne sont pas comparables (jeu de données, configuration, version de PineTS, exécuteur ou schéma de normalisation différents, run qui n'est pas `PINETS_EXECUTION_PASS`, rapport inutilisable), contrôle refait à chaque appel. `reason` nomme les deux runs et la raison (par ex. « same 30 bars and prices, every timestamp shifted by +365 days »). Cette limite vaut pour chaque sortie : avec une attente par sortie (`expect --from-impact`), chaque ligne de `outputs_observed` et de `outputs_not_comparable` le dit. `per_run` donne les faits vérifiés séparément pour chaque run (jeu de données, annexe, points de chaque série). Ne jamais présenter une égalité, une différence ni une première divergence entre ces deux runs ; `what_would_compare` dit ce qu'il faudrait pour comparer ;
     - `incomplete-proof` : une sortie est absente, ambiguë ou partiellement couverte dans l'un des runs ou les deux ; aucune égalité n'est dite pour elle (limite exacte dans `outputs_not_comparable`), les autres sorties restent établies ;
     - `review-output` / `review-objects` / `review-styles` / `check-expected-change` / `read-error` / `read-refusal` / `declare-expectation` / `wait` / `none-possible` : faire ce qui est indiqué ; `missing` dit précisément ce qui manque (résultat périmé, absence de référence, barre indéterminable, attente non déclarée).
   - `applies_to_requested: false` : la recommandation (`earlier_revision_recommendation`) porte sur une autre révision et y reste rattachée ; ne jamais l'appliquer à la révision demandée.
   - Le jugement EXPECTED / UNEXPECTED / UNRESOLVED reste à Claude Code (UNRESOLVED si les preuves ne tranchent pas). La recommandation n'autorise aucune correction, ne fait aucune référence acceptée, ne remplace pas `tv-validate` et ne change aucune calibration. Le navigateur n'est pas nécessaire.
   - Le changement retenu est ensuite reporté dans le source enregistré par les étapes normales (diff contrôlé, guard).
11. Qualifier les résultats PineTS (spec §24.4.7–24.4.9). Correction du source uniquement si elle serait justifiée même sans PineTS (spec §24.4.8) ; puis réexécuter les étapes locales applicables.
12. `tv-validate` selon applicabilité : compilation minimale intermédiaire si l'inventaire l'a conclue requise, campagne fonctionnelle sur le source stabilisé (spec §30.5) ; revalider après toute correction qui change le source. Le regroupement de la campagne suit l'organisation décidée par le titulaire pour ce produit (`DECISIONS.md`), jamais celle d'un autre produit.
13. Mettre à jour uniquement les fichiers contextuels devenus réellement obsolètes (spec §53) ; consigner les quatre mentions de suivi (classe de tâche et niveau, couverture lue, conclusion de benchmark, provenance des rapports d'agents s'il y en a eu) dans l'artefact désigné par le `CLAUDE.md` local du produit. Une unité de travail terminée n'est pas réauditée sans raison nouvelle.
