# Export GitHub

Langue : répondre dans la langue configurée (`language` de `session-status --json`).

Contrat : `tools/pws_workspace/github.py` (docstring) et spec §43.5 amendée le 2026-11-06, protections renforcées le 2026-11-13 après l'audit du 2026-11-12, dépôt réel vérifié avant l'envoi d'un source fermé (I-06, décision du titulaire du 2026-11-13), identité de la destination contrôlée pour **tout** envoi et documents juridiques d'origine des scripts importés exportés à l'identique (demande du titulaire du 2026-11-14). Deux contrôles distincts : l'**identité** du dépôt autorisé (tout envoi, contenu public compris) et la **confidentialité** exigée par un contenu fermé (I-06). Un contenu public peut aller vers une destination publique ou vers un dépôt privé choisi explicitement. Un dépôt privé peut recevoir un source propriétaire si la destination est configurée `private` **et** si GitHub confirme, au moment de l'envoi, que le dépôt réel est privé ; un dossier privé dans un dépôt public n'existe pas. Le dépôt existant du titulaire est une destination à configurer, jamais à restructurer automatiquement.

## Quatre natures d'action, toujours distinguées

| Nature | Ce qui se passe | Commandes |
|---|---|---|
| **Consultation** (aucune écriture) | état de la connexion (`gh` connecté ou credential helper Git ; aucun jeton affiché, stocké ni demandé ; le credential helper n'est montré que par son nom, sans ses arguments, et un assistant en ligne `!…` ou une valeur qui porte un mot de passe ou un jeton est seulement signalé masqué), destinations configurées | `github status`, `github destinations` |
| **Préparation** (écrit des fichiers locaux sous `.claude/runtime/github-export/`, rien n'est envoyé, aucune requête réseau) | plan d'export : destination effective, fichiers inclus (source seulement si `source_visibility: public` ou destination `private` ; documents de release et tutoriel ; conditions référencées par `terms_ref` si c'est un document de conditions reconnu et actuel ; pour un script importé, ses documents juridiques d'origine déclarés, rôle `legal`, à l'identique), fichiers exclus avec motif, avertissements, dossier de staging ; `destination_check` annonce le contrôle d'identité de la destination (`performed: false`) et, si le plan contient un contenu fermé, `visibility_check` annonce le contrôle du dépôt réel (`performed: false`, rien d'observé à ce stade) | `github export-plan --slug <slug> --destination <name>` |
| **Comparaison** (lecture réseau puis lecture locale ; `export-diff` n'écrit rien) | récupération du dépôt distant, puis ajouté / modifié / inchangé par rapport au plan, après revalidation complète ; contrôle de l'identité de la destination pour tout envoi (remote du clone lu localement, `destination_check`) ; quand l'envoi contiendrait un source fermé, lecture en plus de la visibilité réelle sur GitHub (`gh repo view`), présentée dans `visibility_check` | `github fetch --destination <name>`, `github export-diff --slug <slug> --destination <name>` |
| **Exécution** (envoi vers GitHub) | mêmes revalidations que la comparaison, nouveaux contrôles (identité de la destination ; dépôt réel si un source fermé est envoyé) juste avant toute écriture, puis copie du plan dans le clone local, commit, relecture du remote juste avant le push, push de la branche configurée vers `origin` — chaque étape visible | `github publish --slug <slug> --destination <name> --message "…" --yes` |

La gestion des destinations (`github destination-add --name <id> --repo owner/name --visibility public|private [--path-prefix …] [--branch …]`, `destination-remove`) modifie la configuration personnelle : seulement sur décision du titulaire, jamais automatiquement. Retirer ou remplacer une destination invalide ses états locaux (voir plus bas) : l'annoncer avec les chemins rendus.

## Destination effective : toujours la présenter

Le plan, la comparaison et l'envoi rendent `destination` (nom, dépôt `repo`, visibilité, branche, préfixe `path_prefix`, URL de clonage `clone_url`) et, dès qu'un clone existe, `clone` (chemin, `origin` réel, branche, `matches_destination`, travail local non publié). Les présenter au titulaire **avant** toute demande d'autorisation d'envoi, en clair : « dépôt owner/name, **public**, branche main, dossier Published/, clone dont l'origine est … ». Une autorisation ne vaut que pour cette destination effective et ces fichiers.

Pour tout envoi, présenter `destination_check` de la comparaison : dépôt autorisé (`configured.repo`), dépôt réellement désigné par le clone (`remote.repository`), URL de fetch et de push réellement utilisées (`remote.fetch_urls`, `remote.push_urls`), `pushurl` configuré ou réécriture appliquée (`remote.pushurl_configured`, `remote.rewritten`). Ce contrôle établit l'identité du dépôt, pas sa confidentialité.

Quand l'envoi contient un source fermé, présenter aussi `visibility_check` de la comparaison : « dépôt effectif owner/name (`observed.repository`), visibilité observée **PRIVATE** (`observed.visibility`), vérifiée le <AAAA-MM-JJTHH:MM:SSZ> UTC (`checked_at`), URL de push réellement utilisée (`remote.push_urls`) », puis rappeler la limite (`limit`) : la visibilité peut changer entre la vérification et l'envoi ; `publish` vérifie de nouveau immédiatement avant l'envoi, sans garantie atomique avec GitHub. Les URL affichées ne portent jamais d'identifiants (`user:token@` masqué en `***@`) ; ne jamais chercher à les afficher autrement. Seule une partie utilisateur faite de caractères d'identifiants, dans l'autorité, est masquée : une partie que Git ne lit pas comme des identifiants (hôte suivi de `#` ou `?`, `[`, `]`, `\`) reste affichée telle quelle, pour que le véritable hôte ne soit jamais caché derrière `***@github.com` ; la relayer telle quelle au titulaire.

## Revalidations faites par le code (une confirmation `--yes` n'en remplace aucune)

`export-diff` et `publish` relisent la configuration et le manifeste, recalculent le plan et **refusent** quand :

- la destination a changé depuis le plan (nom, dépôt, visibilité, branche, préfixe, URL) ou n'est plus configurée ;
- la visibilité du source a changé, ou le source fermé figurerait dans un plan pour une destination publique ;
- un fichier inclus a changé dans le produit, ou un fichier préparé (staging) a été altéré ;
- le plan date d'une version antérieure, ou a été invalidé ;
- le clone local n'est pas un vrai dossier Git dont l'`origin` est l'URL configurée, sur la branche configurée (clone périmé d'une ancienne destination) ;
- le clone contient un travail local non publié (modification non commitée ou non suivie, commit absent d'`origin`, remise `stash`) — par exemple après un push échoué.

Chaque refus indique l'action : refaire `export-plan` (plan périmé), refaire `fetch` (clone périmé : un clone propre d'un autre dépôt est mis de côté sous `clones/.stale/`, jamais supprimé), ou inspecter le clone dont le chemin est donné et traiter soi-même son travail non publié. Relayer ces messages tels quels, sans les contourner.

## Tout envoi : identité de la destination (demande du titulaire du 2026-11-14)

Pour **tout** envoi — source et documents publics compris — `export-diff` (contrôle présenté dans `destination_check`) et `publish --yes` (condition refaite juste avant toute écriture dans le clone) **refusent** quand le remote du clone n'a pas exactement une URL de fetch et une URL de push telles que Git les utilise réellement (`pushurl`, réécritures `insteadOf` / `pushInsteadOf` appliquées, y compris depuis la configuration Git globale), ou quand ces URL et l'URL de la destination ne désignent pas, sous l'une des formes strictes ci-dessous, le dépôt configuré pour la destination. C'est le même et unique contrôle du remote que celui du source fermé (aucun second mécanisme) ; GitHub n'est pas interrogé pour un contenu public. Ce contrôle refuse aussi une entrée d'URL vide et tout réglage qui ferait se connecter Git ailleurs que l'URL affichée ou sans la vérifier (`core.sshCommand`, `core.gitProxy`, `remote.origin.vcs`, `http.curloptResolve`, `http.sslVerify` à faux, variables `GIT_SSH`, `GIT_SSH_COMMAND`, `GIT_PROXY_COMMAND`, `GIT_SSL_NO_VERIFY`, quelle que soit leur portée) : demander au titulaire de les retirer lui-même pour l'envoi. Ce qui part est exactement le plan : une cible dont le nom ne diffère que par la casse d'une entrée du dépôt, ou qui exige un dossier là où le dépôt a un fichier, est refusée ; un fichier dont Git modifierait les octets au commit (conversion des fins de ligne, filtre de `.gitattributes` ou de la configuration, par exemple `core.autocrlf`) est refusé avant toute écriture (`content_check`) ; aucun hook ne s'exécute lors du commit et du push du clone ; le commit local est vérifié avant le push (un seul nouveau commit, seulement les chemins du plan, chacun avec ses octets exacts). `publish` relit ensuite le remote juste avant `git push` : s'il a changé après le commit local, **rien n'est poussé** et le résultat décrit l'état laissé sur disque (`state_left` : clone, branche, commit, fichiers écrits, travail non publié tel que Git le rapporte, plan conservé, étapes suivantes) — le relayer tel quel ; le commit reste un travail non publié que le titulaire inspecte et abandonne lui-même avant un nouveau `fetch`. Limites (`limit`) : un changement fait dans l'instant entre cette dernière lecture et le push lui-même n'est pas détecté ; le contrôle est hors ligne : il ne voit ni un dépôt renommé ou transféré sur GitHub (GitHub redirige les opérations Git), ni la configuration du client SSH (`~/.ssh/config`) — l'authenticité de github.com repose sur la vérification de la clé d'hôte SSH ou du certificat TLS —, ni un environnement compromis.

## Source fermé : dépôt réel vérifié sur GitHub avant l'envoi (I-06)

Un envoi contient un source fermé quand un de ses fichiers est le source du produit dont la `source_visibility` n'est pas `public`, le source public d'un produit qui reproduit le source fermé d'un autre produit (copie, ou trois lignes de code), ou un document qui porte du code Pine d'un source fermé (même jugement que vers une destination publique), les manifestes étant relus à ce moment-là. Pour un tel envoi, `export-diff` (observation présentée) et `publish --yes` (condition, refaite juste avant toute écriture dans le clone) **refusent** quand :

- la destination n'est pas déclarée `private`, ou la visibilité du source a changé depuis le plan ;
- (contrôle d'identité commun à tout envoi, ci-dessus) le remote du clone n'a pas exactement une URL de fetch et une URL de push telles que Git les utilise réellement (`pushurl`, réécritures `insteadOf` / `pushInsteadOf` appliquées), ou ces URL (l'URL de la destination aussi) ne sont pas écrites **exactement** sous l'une des formes admises désignant le dépôt configuré : `https://github.com/<owner>/<repo>[.git][/]`, `git@github.com:<owner>/<repo>[.git]` ou `ssh://git@github.com/<owner>/<repo>[.git]` — sans identifiants ni autre partie utilisateur, sans port (même par défaut), requête, fragment ni encodage `%`, schéma et hôte en minuscules. Plusieurs URL de push, toute autre forme, autre hôte, autre dépôt, remote illisible : refus, GitHub n'est alors même pas interrogé, et le refus nomme l'hôte que Git contacterait réellement (`host for git: …`, lu comme Git le lit : pour https, l'autorité s'arrête au premier `/`, `?` ou `#`) — le présenter tel quel au titulaire ;
- `gh repo view https://github.com/<owner>/<repo> --json nameWithOwner,visibility,isPrivate,url` (authentification `gh` courante ; jamais `gh api`) ne rapporte pas ce dépôt lui-même comme **PRIVATE** avec `isPrivate: true` : dépôt public ou interne, renommé ou transféré (redirection), introuvable ou invisible avec l'authentification courante, `gh` absent ou non authentifié, erreur, délai dépassé, réponse invalide ou incohérente.

Ni la déclaration `private`, ni un résultat antérieur (plan, comparaison), ni une confirmation `--yes` ne remplacent ce contrôle : `publish` interroge GitHub à chaque envoi et relit l'URL de push juste avant `git push`. Un refus de `publish` n'écrit rien dans le clone et n'envoie rien. Si `gh` manque ou n'est pas authentifié, demander au titulaire de l'installer ou de s'authentifier lui-même (`! gh auth login`). Limite à rappeler : la visibilité peut changer entre le contrôle et l'envoi ; seules des opérations locales (copie, commit) les séparent, sans garantie atomique avec GitHub.

## États périmés : invalider sans supprimer

- `destination-remove` (et `destination-add` sur un nom qui garde des restes d'une destination différente) renomme les plans concernés en `PLAN.invalidated.json` et met de côté un clone propre sous `.claude/runtime/github-export/clones/.stale/` ;
- un clone qui contient un travail local non publié (ou dont Git ne peut établir l'état) n'est **jamais** déplacé ni supprimé : il est marqué (`clones/<name>.STALE.json`), refusé par `fetch`, `export-diff` et `publish`, et son chemin est donné au titulaire avec l'action (inspecter, publier ou abandonner ce travail lui-même, puis déplacer ou supprimer le dossier) ;
- l'entretien ne nettoie pas ces dossiers : ils restent jusqu'à la décision du titulaire.

## Contenus : ce que le plan exclut, avec son motif

- un produit dont la licence existante importée est « à analyser » (`license_release_blockers`) : l'export entier est refusé jusqu'à ce que le titulaire enregistre la licence exacte (`license confirm --license-id`) ;
- un script importé dont les documents juridiques d'origine ne sont pas réglés — noms `LICENSE`, `LICENCE`, `COPYING`, `COPYRIGHT`, `NOTICE`, `PATENTS`, `AUTHORS`, `CREDITS`, `ATTRIBUTION`, `CONTRIBUTORS`, `THIRD_PARTY_NOTICES` et variantes, déclarables à la racine ou directement sous `release/`, textes `LICENSES/<licence>.txt` ; candidats cherchés dans tout le produit sauf `research/`, `validation/` et `tests/` : l'export entier est refusé (`legal_documents.blockers`, jamais un ensemble incomplet) tant que les documents ne sont pas déclarés (`license confirm --license-document <chemin>` répétable, ou `--no-license-documents`), qu'un fichier de nom juridique trouvé n'est pas déclaré ou ne peut pas l'être là où il est (mal placé, dossier, `LICENSES/` ou `release/` qui est un lien : le titulaire le déplace), ou qu'un document déclaré est absent, modifié, lien symbolique ou physique, fichier spécial, vide, binaire, en UTF-16/32 ou dans un encodage non compatible ASCII, porte un bandeau ou une syntaxe de modèle PWS, ou porte vers une destination publique du code Pine d'un source fermé. Un document accepté est exporté à l'identique (nom, octets, encodage, langue ; `LICENSES/<nom>` conservé), jamais remplacé par un modèle PWS ni comparé à un modèle ; un nom juridique ne suffit jamais à l'inclure. L'identifiant SPDX enregistré ne dit pas à lui seul quels documents la redistribution exige : le titulaire les déclare d'après la distribution d'origine ;
- tout lien symbolique (fichier ou dossier, interne ou externe, y compris un source déclaré qui serait un lien) et tout fichier spécial ;
- tout fichier hors de la liste autorisée, comparée sur le chemin complet depuis la racine du produit (`docs/…TUTORIAL….md`, `release/…tutorial….md`, documents de release ; jamais `research/docs/…` ni `validation/release/…`) ;
- un document en brouillon : bandeau DRAFT, champ de modèle de licence non rendu (`{{PROVIDER_LEGAL_NAME}}`, `{{YEAR_RANGE}}`…), bloc `[[?…]]` / `[[!…]]`. Les variables d'alerte TradingView (`{{ticker}}`, `{{close}}`…) sont du texte normal ;
- un source dont le texte porte encore un champ de modèle non rendu (en-tête collé avant le rendu) ;
- un `terms_ref` qui ne désigne pas un document de conditions reconnu (`release/EULA.md`, `release/FREE_USE_GRANT.md`, `release/NOTICE.md` ou un document identique au rendu actuel d'un de ces modèles) ; un document de conditions qui n'est plus actuel (champs modifiés depuis sa génération) — signalé dans `warnings` avec la commande de régénération ;
- vers une destination **publique**, pour un produit à source fermé : copie du source, document reproduisant une ligne de code du source ou portant du code Pine (`//@version=`, déclaration `indicator(`/`strategy(`/`library(`, bloc ```pine) ; pour tout produit : document reproduisant le source fermé d'un autre produit ;
- vers une destination **publique**, le source déclaré d'un produit à source public qui reproduit le source fermé d'un autre produit (copie exacte, ou trois lignes de code) : exclu, avec un avertissement ; vers une destination **privée**, il est inclus mais traité comme un contenu fermé (contrôle du dépôt réel ci-dessus, annoncé par `visibility_check`). Deux lignes communes ne font pas une copie ; un faux positif (lignes génériques partagées) se règle en retouchant ces lignes ou en choisissant une destination privée, jamais en contournant le refus ;
- deux fichiers arrivant sous le même nom cible, y compris quand seules les majuscules et minuscules diffèrent : le plan entier est refusé et le plan précédent invalidé ; renommer ou retirer l'un des deux.

## Écrans (textes visibles, Retour partout)

```text
Écran 1 : Consulter la connexion et les destinations · Préparer un export · Suite… · Retour
Écran 2 : Comparer avec le dépôt · Envoyer vers GitHub · Gérer les destinations · Retour
```

- « Consulter la connexion et les destinations » : lecture seule. Si une connexion manque, demander au titulaire de l'établir lui-même (`! gh auth login`), ne pas l'automatiser.
- « Préparer un export » : demande le script (règle action → script) et la destination ; annonce qu'un dossier de staging local est créé ; affiche la destination effective, inclus / exclus avec motifs, avertissements, état du clone s'il existe.
- « Comparer avec le dépôt » : nécessite une destination et un plan ; `fetch` est un acte réseau explicite en lecture (il peut mettre de côté un clone propre périmé : l'annoncer) ; afficher la destination effective et l'origine du clone avec les changements, le contrôle d'identité (`destination_check`) et, pour un source fermé, le dépôt effectif, la visibilité observée et sa date UTC (`export-diff` interroge GitHub en lecture).
- « Envoyer vers GitHub » : proposé seulement quand un plan préparé existe et que la comparaison est acceptée (`ok: true`, contrôle d'identité compris, et contrôle du dépôt réel pour un source fermé) ; ne s'exécute qu'après l'autorisation explicite du titulaire dans la conversation, **pour ce plan précis** (destination effective, fichiers inclus, message) ; le `git push` reste soumis à la confirmation de permission. Une sélection de menu ne vaut jamais autorisation. Après l'envoi, présenter le `destination_check` et, le cas échéant, le `visibility_check` du résultat (nouvelle observation, nouvelle date). Si le push échoue, ou si le remote a changé après le commit (`state_left`), le commit reste dans le clone comme travail non publié : le dire, avec le chemin et l'état décrit.

L'absence d'autorisation d'envoi n'interdit ni la consultation, ni la préparation, ni la comparaison : seules les écritures sont annoncées comme telles (dossier de staging, configuration, mise de côté d'un clone), et seul l'envoi exige l'autorisation. Une restriction décidée pour une session n'est pas une interdiction du produit.

## Interdits

- Exporter le workspace, `pws.config.json`, `.claude/`, `docs/maintenance/`, des archives, des preuves de validation, des liens symboliques ou tout secret.
- Exporter un source `closed` vers une destination `public`, directement ou indirectement (lien, copie, extrait de code dans un document, source d'un produit public qui le reproduit) ; exporter un document légal en brouillon ou non actuel.
- Modifier, traduire, réencoder, renommer ou remplacer par un modèle PWS un document juridique d'origine d'un script importé ; déclarer un document pour faire passer un plan sans que le titulaire l'ait identifié comme document de cette licence ; présenter l'identifiant SPDX comme suffisant pour établir les obligations de redistribution.
- Envoyer vers un dépôt dont l'identité n'est pas établie comme celle de la destination configurée, ou contourner le contrôle d'identité (modifier le remote ou un réglage de transport pour le faire passer puis le rétablir, pousser à la main depuis le clone) ; modifier les attributs ou la configuration Git d'un dépôt à la place du titulaire pour faire passer un fichier.
- Contourner un refus de revalidation (modifier PLAN.json, le staging ou le clone à la main, réutiliser un plan invalidé) ; supprimer ou déplacer soi-même un clone qui contient un travail non publié.
- Remplacer le contrôle du dépôt réel par une déclaration, un ancien résultat ou une confirmation du titulaire ; interroger GitHub par `gh api` (interdit par les règles du projet) ; afficher une URL avec ses identifiants ou un jeton.
- Retirer des fichiers, réécrire l'historique ou changer la visibilité d'un dépôt : hors périmètre de cette skill (actes du titulaire). Si GitHub rapporte un dépôt public pour une destination déclarée `private`, le signaler au titulaire tel quel ; la correction (rendre le dépôt privé, ou changer de destination) lui appartient.
